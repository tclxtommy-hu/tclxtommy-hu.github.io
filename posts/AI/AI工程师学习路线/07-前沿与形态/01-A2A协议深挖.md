# A2A 协议深挖

> 最后修改时间：2026-10-07 21:33

> 一句话定义： **A2A** /ˌeɪ tuː ˈeɪ/ （ **Agent-to-Agent** /ˈeɪdʒənt tuː ˈeɪdʒənt/ ，Agent 间互操作协议）是让不同厂商、不同框架的 Agent 互相发现能力、委派任务、交换结果的标准——**MCP 连工具，A2A 连 Agent**。

---

## 一、问题背景：为什么需要 A2A

### 1.1 现状痛点

2025 年之前的 Agent 生态是「孤岛式」的：

- **工具层已标准化**：Anthropic 的 MCP（Model Context Protocol，模型上下文协议）解决了「Agent ↔ 工具」的连接问题，社区 Server 一次封装处处可用。
- **Agent 层仍是孤岛**：你公司用 LangGraph 编排 Agent，供应商 A 用 ADK 封装了一个「发票识别 Agent」，供应商 B 用自家框架封装了「费用报销 Agent」——它们之间没有统一的发现、委派、结果回传协议。每对接一家，就要写一套私有集成。

这又是一次经典的 **M×N 集成地狱**：M 个 Agent 框架 × N 个外部 Agent，两两对接成本是 M×N；标准化后降为 M+N。

### 1.2 与 MCP 的分层

```text
┌─────────────────────────────────────────┐
│  Agent A（委派方，Client 角色）          │
└──────────────┬──────────────────────────┘
               │  A2A：跨厂商 Agent 发现 / 委派 / 结果回传
┌──────────────▼──────────────────────────┐
│  Agent B（执行方，Server 角色）          │
└──────────────┬──────────────────────────┘
               │  MCP：Agent 连接工具 / 数据源
┌──────────────▼──────────────────────────┐
│  工具（查库、搜索、发邮件…）             │
└─────────────────────────────────────────┘
```

| 维度 | MCP | A2A |
|------|-----|-----|
| 解决什么 | Agent ↔ 工具/数据 | Agent ↔ Agent |
| 对等关系 | Client 调用 Server | Client Agent 委派 Remote Agent |
| 能力描述 | Tools / Resources / Prompts | Agent Card |
| 交互单位 | 一次工具调用 | Task（可长时、多轮、有产物） |
| 谁提的 | Anthropic（2024） | Google（2025，后捐 Linux Foundation） |
| 关系 | **互补而非竞争**：一个 Agent 往往既是 A2A Server 又是 MCP Client | 同左 |

一句话：**MCP 让 Agent 会用工具，A2A 让 Agent 会找同事**。

### 1.3 什么时候不需要 A2A

A2A 是 **跨信任边界** 的协议。如果所有 Agent 都跑在你自己的进程/集群里，直接函数调用或消息总线（如 12 模块 Skill Router）更快、更简单。选型见第七节。

### 1.4 常见困惑：MCP 和 RPC / HTTP 接口有什么区别

这是最容易混淆的一点：MCP **不是**和 HTTP/RPC 并列的「传输方式」，而是跑在 HTTP（或 stdio）之上的 **Agent 语义协议**。

| 维度 | TCP / HTTP / RPC | MCP |
|------|------------------|-----|
| 层次 | 传输/调用机制（怎么把请求送到对面） | 语义协议（跑在 HTTP 或 stdio 之上） |
| 谁写的调用方代码 | 人写的固定客户端代码 | **LLM** /ˌel el ˈem/ 运行时动态决定调什么、传什么参数 |
| 接口发现 | OpenAPI/WSDL，人读文档后人写代码对接 | `tools/list` 动态发现，schema 直接喂给模型 |
| 调用决策 | 程序逻辑预先写死（`if x then callFoo()`） | 模型根据用户意图推理选工具（Function Calling） |
| 权限模型 | 通常靠网关 | 客户端侧集中做「模型发起的调用」审批 |

用接 GitHub 举例：

- **普通 HTTP 接口**：读 REST 文档 → 人写 `createIssue()` → 程序在某个 `if` 分支里调用。模型根本不知道接口存在。
- **RPC（如 gRPC）**：proto 定义服务 → 生成客户端 stub → 还是人写代码决定何时调用，只是合同更严格。
- **MCP**：工具方暴露 `create_issue` 工具 + JSON Schema → Agent 启动时 `tools/list` 拿到描述 → **模型**看到「帮我提个 bug」，自己推理出该调它、参数怎么填。

一句话：**HTTP/TCP 是「路」，RPC 是「按合同送货」，MCP 是「把货架动态展示给模型，让它自己挑货」**。传输还是那套 HTTP，但调用方从「编译期的人」换成了「推理期的模型」。

## 二、核心概念：Agent Card / Task / Message / Artifact

A2A 的对象模型很小，四个概念讲清楚：

### 2.1 Agent Card（能力发现）

每个 A2A Server 在固定路径暴露一份自描述 JSON，默认为：

```text
https://agent.example.com/.well-known/agent.json
```

Agent Card 告诉对方「我是谁、我能干什么、怎么调我」：

```json
{
  "name": "invoice-agent",
  "description": "识别增值税发票并结构化返回金额、税号、明细",
  "url": "https://agent.example.com/a2a",
  "version": "1.2.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true
  },
  "defaultInputModes": ["text/plain", "application/pdf"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "invoice_ocr",
      "name": "发票识别",
      "description": "输入 PDF 或图片发票，输出结构化 JSON",
      "examples": ["帮我识别这张发票并核对税号"]
    }
  ],
  "authentication": {
    "schemes": ["bearer"]
  }
}
```

发现流程：Client 拉取 `.well-known/agent.json` → 解析 skills → 决定是否委派。类比 MCP 的 `tools/list`，但粒度是「Agent 能力」而非「单个函数」。

### 2.2 Task（任务对象）

A2A 的交互单位不是一次函数调用，而是一个 **有生命周期的 Task**：

- 状态机：`submitted → working → input-required → completed / failed / canceled`
- `input-required`：执行方中途要补充信息（如「发票第二页模糊，请重传」）。
- 长任务支持：Task 可能跑几分钟到几小时，靠轮询、SSE 流或 Push Notification 拿进展。

### 2.3 Message 与 Artifact

- **Message**：双方的对话轮次，含 role（`user` / `agent`）与多个 Part。
- **Part**：内容块，可以是 `text`、`file`（含字节或 URI）、`data`（结构化 JSON）。
- **Artifact**：Task 的 **最终产物**（区别于过程消息），如结构化发票 JSON、生成的报表文件。一个 Task 可产出多个 Artifact。

记住分工：**Message 是过程，Artifact 是交付物**。

## 三、传输与调用方式

- 底层协议： **HTTP** /ˌeɪtʃ tiː tiː ˈpiː/ + **JSON** /ˈdʒeɪsən/ RPC，天然可过网关、CDN、负载均衡。
- 三种取结果方式：
  1. **同步**：请求-响应直接拿到结果（短任务）。
  2. **流式（SSE）**：长任务实时吐状态与中间输出，对应 Agent Card 里的 `streaming: true`。
  3. **推送（Push Notification）**：执行方主动回调 Client 注册的 Webhook，适合分钟级以上任务。

对比 MCP 的 stdio 传输：MCP 可以本地进程间通信，A2A 因为跨厂商，**只有 HTTP 一种主战场**，安全因此更关键。

## 四、安全：身份、授权、审计

A2A 的安全模型一句话：**像开放 API 一样对待每一个远程 Agent**。

### 4.1 三道防线

| 层 | 做法 | 类比 |
|----|------|------|
| 身份（Authentication） | Agent Card 声明认证方式；生产用 **OAuth** /ˈəʊɔːθ/ 2.0 / **mTLS** /ˌem tiːiː el ˈes/ 双向证书；禁止裸 HTTP | API 网关鉴权 |
| 授权（Authorization） | 最小权限：只委派「本任务必需」的数据；能传引用（URI）就不传全文 | IAM scope |
| 审计（Audit） | 双方各自落盘：谁、何时、委派了什么、传了什么数据、结果如何 | 审计日志 |

### 4.2 特有风险

- **提示注入跨边界传播**：恶意指令可借 A2A 从一个 Agent 注入另一个 Agent 的上下文。对策：执行方对入参做不可信数据处理，委派方对返回结果同样不可信。
- **数据外流**：跨厂商委派 = 数据出境给第三方。涉及 PII（个人敏感信息）时必须脱敏或签 DPA。
- **委派链过长**：A 委派 B、B 再委派 C，责任边界模糊。生产建议限制委派深度并要求透传 trace 上下文（如 W3C `traceparent`）。

## 五、贯穿案例：费用报销系统

用一个带真实数字的场景把概念串起来。

**背景**：某 300 人公司，财务每月人工处理约 800 张发票，每张平均 6 分钟，月成本约 80 小时。公司有两个现成资产：

- 自建「报销编排 Agent」（LangGraph，跑在内网）；
- 采购的 SaaS「发票识别 Agent」（供应商 A，暴露 A2A 接口）。

**A2A 委派流程**：

```text
员工上传发票 PDF
   │
   ▼
报销编排 Agent（Client）
   1. GET https://vendor-a.com/.well-known/agent.json   ← 发现
   2. 校验 skills 里有 invoice_ocr、authentication 是 bearer
   3. message/send：委派 Task「识别发票 INV-2026-0930」  ← 委派
   4. 收到 artifact：{ total: 3860.00, taxNo: "91xxxx..." }
   5. 本地规则核对预算科目，走审批流
   │
   ▼
审批通过，自动记账（合计耗时 40 秒/张，对比人工 6 分钟）
```

关键点：编排 Agent **不需要知道** 供应商 A 内部用什么框架/模型——它只面对 Agent Card 和 Task 协议。明年换供应商 B，只要 B 也支持 A2A，集成代码基本零改动。

## 六、最小互通示例（TypeScript）

以下示例演示「拉 Agent Card → 委派 Task → 处理 Artifact」的 Client 侧最小实现（Server 侧同理：一个 HTTP 路由 + 状态机）。可直接用 Node.js 18+ 运行，无第三方依赖。

```typescript
// a2a-client.ts
// 主示例（TS）：A2A Client 最小互通实现

/** A2A 核心类型（简化自规范，够本示例用） */
type A2APart =
  | { readonly kind: "text"; readonly text: string }
  | { readonly kind: "data"; readonly data: Record<string, unknown> }
  | { readonly kind: "file"; readonly uri: string; readonly mimeType: string };

interface AgentCard {
  readonly name: string;
  readonly url: string;
  readonly capabilities: { readonly streaming: boolean };
  readonly skills: ReadonlyArray<{ readonly id: string; readonly name: string }>;
}

type TaskStatus = "submitted" | "working" | "completed" | "failed";

interface A2ATask {
  readonly id: string;
  readonly status: { readonly state: TaskStatus; readonly message?: string };
  readonly artifacts?: ReadonlyArray<{
    readonly name: string;
    readonly parts: readonly A2APart[];
  }>;
}

interface SendParams {
  readonly message: {
    readonly role: "user";
    readonly parts: readonly A2APart[];
  };
}

/** 1. 能力发现：拉取 Agent Card */
async function discoverAgent(baseUrl: string): Promise<AgentCard> {
  const res = await fetch(`${baseUrl}/.well-known/agent.json`);
  if (!res.ok) throw new Error(`Agent Card 拉取失败：HTTP ${res.status}`);
  return (await res.json()) as AgentCard;
}

/** 2. 委派任务：message/send（生产中应带 Bearer Token） */
async function sendTask(
  agent: AgentCard,
  token: string,
  invoiceUri: string
): Promise<A2ATask> {
  const params: SendParams = {
    message: {
      role: "user",
      parts: [
        { kind: "text", text: "请识别这张发票并返回结构化结果" },
        { kind: "file", uri: invoiceUri, mimeType: "application/pdf" },
      ],
    },
  };

  const res = await fetch(agent.url, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${token}`,
    },
    body: JSON.stringify({ jsonrpc: "2.0", id: 1, method: "message/send", params }),
  });
  if (!res.ok) throw new Error(`委派失败：HTTP ${res.status}`);

  const body = (await res.json()) as { result: A2ATask };
  return body.result;
}

/** 3. 消费 Artifact：提取结构化发票数据 */
function extractInvoice(task: A2ATask): Record<string, unknown> | null {
  if (task.status.state !== "completed") return null;
  for (const artifact of task.artifacts ?? []) {
    for (const part of artifact.parts) {
      if (part.kind === "data") return part.data;
    }
  }
  return null;
}

// ---- 端到端串联（贯穿案例的代码化） ----
async function main(): Promise<void> {
  const vendor = await discoverAgent("https://vendor-a.com");
  const hasSkill = vendor.skills.some((s) => s.id === "invoice_ocr");
  if (!hasSkill) throw new Error(`${vendor.name} 不具备发票识别能力，拒绝委派`);

  const task = await sendTask(
    vendor,
    process.env.VENDOR_A_TOKEN ?? "test-token",
    "https://internal.corp/uploads/INV-2026-0930.pdf"
  );

  const invoice = extractInvoice(task);
  console.log(
    invoice
      ? `识别完成：金额 ${invoice.total} 元，任务 ${task.id}`
      : `任务未完成，当前状态：${task.status.state}`
  );
}

main().catch((err: unknown) => {
  console.error("[a2a-client] 失败：", err);
  process.exit(1);
});
```

补充（Python）：当团队没有 TS 运行时、只能写运维脚本时，等价逻辑用 `httpx` + `pydantic` 实现即可，协议字段与上面完全一致，只是换成 Python 的类型标注，此处不展开完整代码。

## 七、选型：A2A vs 进程内多 Agent

回答「什么时候需要 A2A，什么时候进程内就够」：

| 判断条件 | 进程内多 Agent（函数调用/消息总线） | A2A |
|----------|-------------------------------------|-----|
| Agent 是否都在自己的代码库/集群内 | ✅ 是 → 不需要 A2A | 跨厂商/跨组织才用 |
| 是否需要运行时能力发现 | 编译期已知，不需要 | 需要拉 Agent Card 动态发现 |
| 任务时长 | 毫秒~秒级 | 分钟~小时级长任务（Task + 推送） |
| 信任边界 | 同一信任域 | 需鉴权、审计、数据合规的开放边界 |
| 变更频率 | 同步发版，接口可控 | 对方独立升级，靠协议版本兼容 |
| 典型例子 | 12 模块 Skill Router、LangGraph 图内节点 | 采购 SaaS Agent、跨部门 Agent 市场 |

**经验法则**：先问「对方是不是独立部署、独立演进的所有者」。是 → A2A；否 → 进程内编排，别为协议开销买单。

## 八、常见困惑：接入一堆 MCP Server，是不是就成了微服务

### 8.1 结构上确实很像

如果一个 Agent 接入了大量 MCP Server（查库、搜索、工单、邮件…），整体形态和微服务架构高度相似：

```text
              ┌────────────┐
              │ Agent 编排层 │  ← 类似 API Gateway / BFF
              └─────┬──────┘
        ┌──────┬────┼────┬──────┐
        ▼      ▼    ▼    ▼      ▼
     MCP    MCP   MCP   MCP   MCP      ← 类似一组微服务
    (DB)  (搜索) (工单) (邮件) (浏览器)
```

所以你的判断对了一半：**某个 MCP Server 挂了，对应那块能力就不可用**——和微服务的部分故障一样。而且 Agent 场景还有三个 **更糟** 的特性：

1. **故障发生在模型推理期**：传统微服务挂了，代码里写的 `if` 分支直接报错；MCP 挂了，模型可能反复重试、换一个近似工具硬凑、或编造参数，先烧一堆 token 再失败。
2. **错误信息要「说给模型听」**：人读的 stack trace 没用，得把失败原因转成模型可理解的反馈（「工单系统不可用，请告知用户稍后再试」），否则模型会继续瞎试。
3. **依赖爆炸更隐蔽**：工具是 `tools/list` 动态发现的，没有编译期检查——某个 Server 悄悄升级挂了，Agent 是运行时才第一次撞上。

### 8.2 但别真的按微服务治理去套

| 维度 | 微服务 | MCP 集群 |
|------|--------|----------|
| 调用方 | 确定性代码 | 会推理、会重试、会幻觉的模型 |
| 接口契约 | 编译期校验 | 运行时发现，弱契约 |
| 爆炸半径 | 某接口 5xx | 某能力不可用 + token 浪费 + 错误行为不可预测 |
| 治理重点 | 限流、熔断、链路追踪 | 同左，**外加**失败信息模型友好化 + 工具列表裁剪 |

### 8.3 工程对策

- **健康检查与熔断**：MCP Server 挂了就从本轮 `tools` 列表里摘掉，别让模型看到「能调但必挂」的工具。
- **超时与重试上限**：模型重试必须由编排层兜底，不能让模型自己无限试。
- **降级话术**：编排层捕获失败后，注入明确指令——「工具 X 当前不可用，请告知用户并询问是否换方案」，而不是把原始错误抛进上下文。
- **链路追踪**：按 [MCP 协议 · §7 调用链路与可观测](../../Agent开发知识/03-工具调用/02-MCP协议.html) 的做法，`traceparent` 贯穿 Client → Server → 下游，否则挂了无法归因。
- **工具列表瘦身**：接入 ≠ 全部暴露，按任务动态裁剪工具，既省上下文也缩小故障面。

一句话：**形态像微服务，故障语义比微服务更「软」——治理手段可以复用（熔断/超时/追踪），但必须额外为「模型的失败反应」做设计**。

## 九、学习要点

- **MCP 连工具，A2A 连 Agent**：两者是互操作两层标准，同一个 Agent 可以同时是 A2A Server 和 MCP Client。
- 四个核心对象：Agent Card（发现）、Task（生命周期）、Message（过程）、Artifact（交付物）。
- Task 是状态机，`input-required` / 流式 / 推送都是为了长任务设计的，这是与「一次函数调用」的本质区别。
- 安全是 A2A 的第一公民：OAuth/mTLS 身份、最小权限授权、双方审计；提示注入会跨边界传播。
- 选型：跨信任边界、需运行时发现、长任务 → A2A；同仓库同集群 → 进程内多 Agent 就够。
- 可观测：委派链上必须透传 `traceparent`，否则跨厂商故障无法归因。
