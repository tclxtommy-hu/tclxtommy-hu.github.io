## 一、任务画像 → 模型能力需求

### 1.1 任务画像四象限

不要直接问「哪个模型最好」，先画任务画像。四个维度足够覆盖 90% 场景：

| 维度 | 关键问题 | 典型取值 |
|------|----------|----------|
| **输入形态** | 多长？多模态？是否含代码/结构化数据？ | 短文本 1k / 长文 32k / 多模态图+文 |
| **输出形态** | 结构化字段？长文生成？多轮对话？需要工具？ | JSON 提取 / 总结 / 对话 / Agent |
| **领域知识** | 通用？垂直（医疗/法律/代码）？需 RAG？ | 通用 / 行业垂直 / 私域 |
| **风险等级** | 错了能不能兜住？幻觉代价多大？ | 低可接受幻觉 / 必须可解释 / 不可错 |

小智的工单提取任务画像示例：

```text
输入：短文本（用户消息 ≤ 500 字，单模态）
输出：JSON 结构化（5 字段，强制 schema）
领域：电商客服（通用 + 私域知识库 RAG 兜底）
风险：中（错填 order_id 后果可控，可二次确认）
```

### 1.2 模型能力需求矩阵

把画像转成能力需求，**逐打分（1~5）**，避免「什么都想要」：

| 能力维度 | 小智需求 | 备注 |
|---------|:---:|------|
| 指令遵循（JSON Schema） | 5 | 必须严格遵守 |
| 中文理解 | 5 | 用户全中文 |
| 通用推理 | 3 | 工单分类不算难 |
| 长上下文（> 32k） | 1 | 输入短，无需 |
| 多模态（图/音） | 1 | 当前只接文本 |
| 工具调用 | 4 | Agent 升级后需要 |
| 代码能力 | 1 | 不涉及 |
| 推理深度（数学/逻辑） | 1 | 不涉及 |

**关键直觉**：当某项需求 ≤ 2 时，别为大模型的「全能」付溢价——小模型在该项上的差距通常 < 5%，而价格差几倍。

### 1.3 落地示例：任务画像评分表

把上面的矩阵写成代码，让选型决策可量化：

```typescript
interface TaskProfile {
  instructionFollow: number; // 1~5
  chineseQA: number;
  reasoning: number;
  longContext: number;     // 1~5，1=无需 5=>128k
  multimodal: number;
  toolUse: number;
  coding: number;
  deepReasoning: number;   // 数学/逻辑/o1 类需求
}

// 模型能力画像（手工标定或评测得出）
interface ModelCard {
  name: string;
  scores: TaskProfile;
  inputPricePer1k: number;  // USD / 1k tokens
  outputPricePer1k: number;
  avgLatencyMs: number;
  supportsTools: boolean;
  contextWindow: number;
}

function matchModels(
  task: TaskProfile,
  models: ModelCard[],
  minScore = 3, // 每项需求最低可接受分数
): ModelCard[] {
  return models.filter((m) => {
    return Object.entries(task).every(([k, need]) => {
      if (need <= 2) return true; // 需求低不卡
      return m.scores[k as keyof TaskProfile] >= Math.min(need, minScore);
    });
  });
}
```

**注意**：`minScore = 3` 是兜底——某项需求 5 但所有模型都得 4 分时，宁可放宽也不要直接淘汰所有候选。

## 二、小模型 / 大模型 / 推理模型何时

### 2.1 三类模型的能力—成本曲线

按 2026 年的市场价（USD / 1M tokens，input + output 加权），模型大致分三档：

| 类别 | 代表 | 价格区间 | 能力上限 | 典型延迟 |
|------|------|:---:|------|:---:|
| **小模型**（≤ 14B） | gpt-4o-mini、Qwen2.5-7B、Llama-3.1-8B、DeepSeek-V3 | $0.15 ~ $0.80 | 70~80% 通用任务 | 0.4~0.8s |
| **大模型**（70B~400B） | gpt-4o、Claude Sonnet、Gemini 1.5 Pro、Qwen2.5-72B | $3 ~ $15 | 85~92% | 0.8~2s |
| **推理模型**（test-time compute） | OpenAI o1/o3、DeepSeek R1、Claude Extended Thinking | $15 ~ $60 | 90~95%（数学/代码/逻辑） | 5~30s |

价格差 **100 倍**，能力上限差 **20pp**——多数业务根本用不上顶部那 5pp。

### 2.2 决策树：什么时候用谁

```text
任务进来
  │
  ├── 需要长链推理（多步逻辑/数学/代码竞赛）？
  │     └── 是 → 推理模型（限定场景，且设思考预算）
  │
  ├── 输入长（> 32k）且需要「通读后回答」？
  │     └── 是 → 大模型（或带长上下文优化的小模型）
  │
  ├── 任务简单可模板化（分类/提取/短摘要）？
  │     └── 是 → 小模型（首选自托管或 mini 系列）
  │
  └── 复杂生成（长文写作/规划/多步推理但非数学）？
        └── 大模型
```

**重要原则**：**推理模型不是越大越好**——简单任务用推理模型会「想偏」（见[《推理模型》](../../AI知识库/15-前沿与趋势/01-推理模型.html) 第 5 节）。小智只在「退款争议判定」一个子任务用 R1，其他仍走小模型。

### 2.3 混合路由：同一个产品多模型

**这是本题第一个学习要点的核心**：答案是「能，而且应该」。

小智 v2 的真实路由配置：

```typescript
type TaskType = "intent" | "extraction" | "answer" | "dispute" | "summary";

interface RouteRule {
  task: TaskType;
  model: string;
  fallbackModel: string;
  maxRetries: number;
}

const ROUTES: RouteRule[] = [
  // 分类路由：简单分类走 mini，省 90% 成本
  { task: "intent",     model: "gpt-4o-mini",   fallbackModel: "gpt-4o",         maxRetries: 1 },
  // 字段提取：需要结构化能力，用 4o 保证 schema 合规
  { task: "extraction", model: "gpt-4o",        fallbackModel: "gpt-4o-mini",    maxRetries: 2 },
  // 自由回答：中等难度生成，用 4o
  { task: "answer",     model: "gpt-4o",        fallbackModel: "claude-sonnet",  maxRetries: 1 },
  // 退款争议：需要推理深度，用推理模型
  { task: "dispute",    model: "deepseek-r1",   fallbackModel: "gpt-4o",         maxRetries: 1 },
  // 摘要：模板化短任务，自托管小模型
  { task: "summary",    model: "qwen2.5-7b",    fallbackModel: "gpt-4o-mini",    maxRetries: 1 },
];
```

**落地效果**：

- 80% 的请求走小模型（intent + summary），平均成本 $0.0003
- 18% 走大模型（extraction + answer），平均成本 $0.006
- 2% 走推理模型（dispute），平均成本 $0.04
- 加权平均 $0.0014/请求，比 v1 全用 gpt-4o 降 67%

**路由的入口实现**见[《LLM 网关与路由》](04-LLM网关与路由.html)。

### 2.4 路由决策的坑

| 坑 | 现象 | 规避 |
|---|------|------|
| **路由过粗** | 「简单/复杂」二分，复杂类被大模型烧钱 | 用任务级路由（按业务子任务分），不用难度分级 |
| **路由过细** | 每个分支都接微调模型，运维爆炸 | 控制在 3~8 条路由，超出说明任务切分有问题 |
| **fallback 链雪崩** | 主模型挂 → fallback 挂 → 用户超时 | fallback 必须异步探活，不只是配置多一条 |
| **无监控盲区** | 某条路由悄悄坏掉没人发现 | 每条路由都接 P99 延迟 + 业务指标告警 |

### 3.2 数据驻留决策树

数据合规是第一约束，不是优化项：

```text
数据是否含个人信息（PII）/（PHI）/（金融客户数据）？
  │
  ├── 否 → 任意方案
  │
  └── 是
        │
        ├── 法规要求数据不出境（如金融、医疗、政务）？
        │     └── 是 → 私有化部署 / 国内 API（Qwen/GLM/DeepSeek）
        │
        └── 仅要求「不用于训练」+ 加密传输？
              └── 海外 API 即可，但合同里必须写清
```

小智的客户群里有医院，问答内容含病历字段 → **必须国内自托管**。这就是为什么「summary」路由用 Qwen2.5-7B 自托管而不是 gpt-4o-mini——合规成本算进选型。

### 3.3 中转站与多上游策略

小智 v3 用了 LiteLLM + 三个上游：OpenAI（主力）、阿里云 DashScope（中文路由备份）、自托管 vLLM（私有化路由）。三个理由：

1. **不把鸡蛋放一个篮子**：某厂商宕机或限流，业务不会停；
2. **按场景挑上游**：英文用户 → OpenAI；中文+合规 → DashScope；高敏感 → 自托管；
3. **谈判筹码**：能基于价格动态调度，逼厂商给出更好的企业价。

配置示例（LiteLLM `config.yaml` 简化）：

```yaml
model_list:
  - model_name: gpt-4o
    litellm_params:
      model: openai/gpt-4o
      api_key: os.environ/OPENAI_API_KEY

  - model_name: qwen-72b
    litellm_params:
      model: openai/qwen2.5-72b-instruct
      api_key: os.environ/DASHSCOPE_API_KEY
      api_base: https://dashscope.aliyuncs.com/compatible-mode/v1

  - model_name: qwen-local
    litellm_params:
      model: openai/qwen2.5-7b-instruct
      api_base: http://vllm.internal:8000/v1
      api_key: "EMPTY"

router_settings:
  num_retries: 2
  timeout: 30
  fallbacks:
    - qwen-72b: ["gpt-4o", "qwen-local"]
    - gpt-4o: ["qwen-72b", "qwen-local"]
```

**注意**：私有化路由在故障时**绝不**回退到海外 API（合规不允许），而是降级到「转人工」。

## 四、评测集怎么帮你选型（别只看榜）

### 4.1 公开榜的三个陷阱

**LMSYS Chatbot Arena** /ˈɑːrənə/ 、 **MMLU** /ˌem em luː ˈluː/ 、 **HumanEval** 等公开榜是必要参考，但**不能直接当决策依据**：

| 陷阱 | 真实代价 |
|------|----------|
| **分布漂移** | 榜上是英文 + 通用对话，你的业务是中文 + 电商客服——可能差 20pp |
| **数据污染** | 2025 年起多家模型疑似针对公开榜过拟合，第三方独立评测陆续发现榜单虚高 |
| **能力≠成本** | 榜只反映能力上限，不告诉你「差 2pp 要多付 10 倍」 |

小智 v1 直接按榜选 gpt-4o，结果在电商场景准确率 78%——比内部评测的 Claude Sonnet 低 6pp。

### 4.2 自建评测集三要素

可靠的选型评测集要满足三件事：

| 要素 | 要求 | 反例 |
|------|------|------|
| **分布贴合业务** | 真实流量采样 + 标注，覆盖率 > 80% 子任务 | 拿 Wikipedia 段落当工单提取评测 |
| **可量化打分** | 每条样本有标准答案或人标等级（1~5） | 只用「看着不错」打分 |
| **稳定可重跑** | 同一模型同一版本多次跑分差异 < 1pp | 跑一次就下结论 |

小智的评测集结构：

```text
evals/
├── ticket-extraction/    # 工单提取（结构化）
│   ├── 500 条真实样本（去标识化）
│   ├── gold.json（人工标注）
│   └── judge_prompt.md（评分 prompt）
├── intent-classify/     # 意图分类
├── dispute-judge/       # 退款争议判定
└── safety/              # 红队与越狱
```

### 4.3 落地示例：模型横评脚本

跑一次所有候选模型在同一评测集上的表现，输出对比表：

```typescript
import OpenAI from "openai";
import Anthropic from "@anthropic-ai/sdk";
import { promises as fs } from "fs";

interface EvalCase {
  input: string;
  expected: Record<string, unknown> | string;
}

interface EvalResult {
  model: string;
  caseCount: number;
  passRate: number;        // 0~1
  avgLatencyMs: number;
  totalCostUsd: number;
  errors: { caseIdx: number; reason: string }[];
}

async function runEval(
  modelName: string,
  cases: EvalCase[],
  runner: (input: string) => Promise<{ output: string; tokens: number; latencyMs: number; costUsd: number }>,
): Promise<EvalResult> {
  const results: { pass: boolean; latencyMs: number; costUsd: number }[] = [];
  const errors: EvalResult["errors"] = [];

  for (let i = 0; i < cases.length; i++) {
    const c = cases[i];
    try {
      const { output, latencyMs, costUsd } = await runner(c.input);
      const pass = judge(output, c.expected); // 你的判定函数
      results.push({ pass, latencyMs, costUsd });
      if (!pass) errors.push({ caseIdx: i, reason: "judge failed" });
    } catch (e) {
      errors.push({ caseIdx: i, reason: String(e) });
    }
  }

  const passRate = results.filter((r) => r.pass).length / cases.length;
  return {
    model: modelName,
    caseCount: cases.length,
    passRate,
    avgLatencyMs: results.reduce((s, r) => s + r.latencyMs, 0) / results.length,
    totalCostUsd: results.reduce((s, r) => s + r.costUsd, 0),
    errors,
  };
}

async function compareModels(cases: EvalCase[]) {
  const candidates = [
    { name: "gpt-4o",         runner: runOpenAI("gpt-4o") },
    { name: "gpt-4o-mini",    runner: runOpenAI("gpt-4o-mini") },
    { name: "claude-sonnet",  runner: runAnthropic("claude-3-5-sonnet") },
    { name: "qwen-72b",       runner: runDashScope("qwen2.5-72b-instruct") },
  ];

  const results = await Promise.all(
    candidates.map((c) => runEval(c.name, cases, c.runner)),
  );

  // 按 passRate × 成本性价比排序输出
  results.sort((a, b) => (b.passRate / Math.max(a.totalCostUsd, 0.01))
                     - (a.passRate / Math.max(b.totalCostUsd, 0.01)));

  await fs.writeFile("eval-report.json", JSON.stringify(results, null, 2));
  console.table(results.map((r) => ({
    model: r.model,
    passRate: (r.passRate * 100).toFixed(1) + "%",
    avgLatencyMs: r.avgLatencyMs.toFixed(0),
    totalCostUsd: "$" + r.totalCostUsd.toFixed(4),
  })));
}

function judge(output: string, expected: unknown): boolean {
  // 简单实现：JSON 提取后做字段匹配
  // 复杂场景可调 LLM 做语义判定（"LLM as judge"）
  try {
    const got = JSON.parse(output);
    return JSON.stringify(got) === JSON.stringify(expected);
  } catch {
    return output.trim() === String(expected).trim();
  }
}
```

**运行纪律**：

1. **固定版本**：锁定 `gpt-4o-2025-01-15` 这类带日期的照，别用别名；
2. **固定随机**：设 `temperature = 0`（评测场景）或跑 3 次取均值；
3. **同时打基线模型**：每次评测都把当前生产模型跑一遍当对照，否则无法判断「新模型好 2pp 是真提升还是运气」。

### 4.4 用 LLM 当裁判的边界

「LLM as judge」可以省人工，但要清楚它的偏置：

- **位置偏置**：偏好第一个选项的倾向约 5~15%；
- **自利偏置**：倾向于给同厂商模型高分（GPT-4 评 GPT-4 比评 Claude 平均高 8pp）；
- **长度偏置**：偏向给更长答案高分。

**规避**：交叉裁判（GPT-4 + Claude 互评）、随机化位置、加长度归一化。

## 五、换模型的回归怎么做

这是本题第二个学习要点。换模型不是上线开关——是**带灰度带监控的工程变更**。

### 5.1 回归三层防线

| 层 | 做法 | 触发条件 |
|----|------|----------|
| **离线** | 跑自建评测集 + 历史 100 条难例 | 任何模型更换前必跑 |
| **影子流量** | 新模型接 5% 流量但不下发，结果存日志对比 | 离线通过后 |
| **灰度** | 5% → 20% → 50% → 100%，每档观察 ≥ 24h | 影子流量无显著差异 |

### 5.2 灰度配置实现

```typescript
interface ShadowConfig {
  candidateModel: string;
  trafficPercent: number;  // 0~100
  bucketKey: "userId" | "sessionId" | "traceId";
  comparisonMetrics: string[];
}

function shouldUseCandidate(
  version: ShadowConfig,
  ctx: { userId?: string; sessionId?: string; traceId?: string },
): boolean {
  // 哈希分桶，保证同一用户/会话始终走同一路由（结果可比）
  const key = ctx[version.bucketKey] ?? ctx.traceId ?? "default";
  const bucket = hashToBucket(key, 100); // 0~99
  return bucket < version.trafficPercent;
}
```

**关键原则**：**始终按 userId/sessionId 哈希分桶**——同一用户两次请求必须走同一型，否则对比数据不可信。

### 5.3 灰度期间的判定指标

至少看 5 项：

| 指标 | 阈值 | 含义 |
|------|------|------|
| 业务准确率 | 不可下降 > 1pp | 模型没变傻 |
| P50/P99 延迟 | 不可上涨 > 20% | 用户没变慢 |
| 单位请求成本 | 不可上涨 > 30%（除非能力提升对得起） | 账本 |
| 用户满意度/CSAT | 不可下降 | 体感 |
| 失败率/Refund 率 | 不准上升 | 没出新事故 |

任一项超阈值立即回滚，**不要心存侥幸**。

### 5.4 回滚机制

```typescript
// 路由层保持热备，新模型挂掉自动回退老模型
const ROUTES_V3: RouteRule[] = [
  { task: "extraction", model: "gpt-4o", fallbackModel: "gpt-4o-mini", maxRetries: 2 },
];

// Feature flag 控制是否启用 v3
if (featureFlags.isEnabled("route-v3")) {
  ROUTES_V3[0].model = "claude-sonnet-4"; // 灰度候选
}
```
