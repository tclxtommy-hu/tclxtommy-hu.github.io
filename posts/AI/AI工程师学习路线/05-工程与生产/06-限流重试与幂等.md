## 〇、贯穿案例：小智重试翻车史

电商客服「小智」真实翻车记录：

| 次 | 场景 | 后果 | 修复 |
|----|------|------|------|
| 1 | 工具 `submit_refund` 重试 3 次都成功调用 | 同一订单退了 2 次钱 | 加幂等键 `order_id + amount` |
| 2 | 嵌入 API 限流，自动重试风暴 | 3 秒内发起 50 次重试，封 IP | 加指数退避 + 抖动 |
| 3 | 用户疯狂点「提交」，9 次重复请求 | 9 条工单进入人工队列 | 拆 + 幂等键 `request_id` |

**关键直觉**：**默认不重试 + 主动设计重试** 比 **默认重试 + 事后排查幂等** 安全得多。

## 一、限流信号与客户端策略

### 1.1 四类限流信号

| 信号 | 来源 | 含义 |
|------|------|------|
| **429 Too Many Requests** | HTTP | 超配额 / QPS / TPM |
| **Retry-After header** | HTTP | 多少秒后可重试 |
| **x-ratelimit-remaining** | HTTP | 剩余配额（预测用） |
| **5xx 连续上升** | HTTP | 服务异常或即将限流 |

### 1.2 客户端处理优先级

```typescript
async function callUpstreamWithRateLimit(req: ChatRequest): Promise<ChatResponse> {
  try {
    return await upstream.chat(req);
  } catch (err) {
    const status = err.status;
    const retryAfter = err.headers?.["retry-after"];

    // 1. 429：读 Retry-After，等足再重试
    if (status === 429 && retryAfter) {
      const waitMs = parseRetryAfter(retryAfter);
      await sleep(waitMs);
      return callUpstreamWithRateLimit(req);  // 递归重试
    }

    // 2. 5xx：指数退避重试
    if (status >= 500) {
      return retryWithBackoff(() => upstream.chat(req));
    }

    // 3. 4xx（除 429）：不可重试
    throw err;
  }
}

function parseRetryAfter(value: string): number {
  // 可能是秒数或 HTTP-date
  const seconds = Number(value);
  if (!Number.isNaN(seconds)) return seconds * 1000;
  return new Date(value).getTime() - Date.now();
}
```

### 1.3 三类限流位置

| 位置 | 作用 | 实现 |
|------|------|------|
| **客户端进程内** | 保护本进程不超并发 | Semaphore / p-limit |
| **网关层** | 全平台配额 | LiteLLM rate limit / 自建 |
| **上游厂商** | 防过载 OpenAI 等 | 自动 |

详见[《LLM 网关与路由》](04-LLM网关与路由.html) §2.3。

## 二、指数退避与抖动

### 2.1 公式

```typescript
function backoffMs(attempt: number, base = 500, cap = 30000, jitter = true): number {
  // 指数：base * 2^attempt
  const exp = Math.min(base * 2 ** attempt, cap);
  // 抖动：random(0.5x, 1.5x) 防雪崩
  return jitter ? exp * (0.5 + Math.random()) : exp;
}

// 示例：attempt=0→~500ms, 1→~1s, 2→~2s, 3→~4s, 4→~8s
```

**为什么必须抖动**：无抖动时，1000 个客户端在同一秒重试 → 同一秒把上游打挂 → 又一起重试 → 雪崩。

### 2.2 实战配置

| 场景 | base | cap | maxAttempts | 说明 |
|------|:---:|:---:|:---:|------|
| LLM 调用 | 500ms | 8s | 3 | 延迟敏感，不重试太多 |
| 工具 HTTP | 200ms | 2s | 3 | 通常很快恢复 |
| 语音 ASR | 1s | 10s | 2 | 重资源，重试代价大 |
| 数据库连接 | 100ms | 5s | 5 | 通常瞬时 |

### 2.3 落地示例：通用重试装饰器

```typescript
async function retryWithBackoff<T>(
  fn: () => Promise<T>,
  opts: { maxAttempts: number; base?: number; cap?: number; shouldRetry?: (e: unknown) => boolean } = { maxAttempts: 3 },
): Promise<T> {
  const { maxAttempts, base = 500, cap = 30000, shouldRetry = () => true } = opts;
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === maxAttempts - 1) throw err;
      if (!shouldRetry(err)) throw err;
      await sleep(backoffMs(attempt, base, cap));
    }
  }
  throw new Unreachable();
}
```

## 三、幂等键设计

### 3.1 幂等的本质

**同一请求执行 N 次效果 = 执行 1 次**——这是分布式系统的基本约束，AI 系统也不例外。

### 3.2 LLM 调用的幂等性

LLM 主调用**天然幂等**：

- 输入确定 → 输出确定（同一模型 + temperature=0）
- 没有副作用（不写库、不发邮件）

**但**：

- `temperature > 0` → 不幂等
- 中间有 RAG 检索 → 检索内容可能变（文档库更新）→ 幂等性弱化

**对策**：需要幂等的任务 set 0 上下文，或在 prompt 加 `timestamp` 防重放。

### 3.3 工具调用的幂等性（**核心难点**）

工具调用有副作用——重试必须靠 **幂等键**：

| 工具类型 | 幂等键构造 | 例子 |
|---------|----------|------|
| **写库** | `table + business_id + version` | `update_user:{userId}:v{version}` |
| **发邮件** | `recipient + subject + body_hash` | `email:{addr}:{hash}` |
| **退款** | `order_id + amount + reason` | `refund:{orderId}:{amount}` |
| **文件上传** | `bucket + path + content_hash` | `upload:{bucket}/{path}:{hash}` |
| **第三方 API** | 厂商提供的 `Idempotency-Key` | Stripe / Shopify 等 |

### 3.4 落地示例：幂等键生成 + 去重

```typescript
import crypto from "crypto";

interface IdempotentCall<T> {
  key: string;
  execute: () => Promise<T>;
  ttlSec: number;  // 去重保留时长
}

async function idempotentExecute<T>(call: IdempotentCall<T>, store: KVStore): Promise<T> {
  // 1. 检查是否已执行过
  const cached = await store.get(call.key);
  if (cached) {
    if (cached.status === "running") throw new ConcurrentExecution(call.key);
    if (cached.status === "done") return cached.result as T;
  }

  // 2. 标记 running（防止并发同 key）
  await store.set(call.key, { status: "running" }, call.ttlSec);

  try {
    const result = await call.execute();
    await store.set(call.key, { status: "done", result }, call.ttlSec);
    return result;
  } catch (err) {
    await store.del(call.key);  // 失败清除，允许重试
    throw err;
  }
}

// 工具侧使用：业务自己生成幂等键，工具内部去重
await idempotentExecute({
  key: `refund:${orderId}:${amount}`,
  execute: () => submitRefund({ orderId, amount, reason }),
  ttlSec: 86400,  // 24h 去重
}, redisKV);
```

### 3.5 幂等键的两个常见错

| 错误 | 后果 |
|------|------|
| 用时间戳当 key | 每次重试时间戳不同 → 双花 |
| 用全量参数拼接 key | 同一逻辑请求因表述差异被当不同 → 漏去重 |
| key 过期太短 | 长流程任务被重试时 key 已失效 → 双花 |
| 没有失败清除 | 失败后永久占位 → 用户无法重试 |

## 四、幂等键放哪一层

这是本题第二个学习要点的核心——答案是**工具 SDK 层** + **网关层** 二选一。

### 4.1 三种放法对比

| 位置 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **业务代码** | 灵活，可控 | 容易漏，重复写 | ❌ 不推荐 |
| **工具 SDK** | 业务零感知，强制 | 工具必须自实现 | ✅ 推荐（自研工具） |
| **网关层** | 跨工具通用 | 工具语义不清，难精确 | ✅ 推荐（通用层兜底） |

### 4.2 推荐：业务提供 key，SDK / 网关执行去重

```typescript
// 业务侧：显式传幂等键
await idempotentExecute({
  key: `refund:${orderId}:${amount}`,   // 业务语义生成
  execute: () => tool.submitRefund({ orderId, amount, reason }),
}, idempotencyStore);   // SDK 提供

// 网关侧：作为最后兜底
// 业务没传 key 时，网关根据方法名 + 参数哈希生成一个
// 24h 内抓相同请求直接返回首次结果
```

### 4.3 自研工具 SDK 的实现示例

```typescript
class IdempotencyMiddleware {
  constructor(private store: KVStore) {}

  wrap<P extends unknown[], R>(keyFn: (...args: P) => string, ttlSec: number, fn: (...args: P) => Promise<R>) {
    return async (...args: P): Promise<R> => {
      const key = keyFn(...args);
      return idempotentExecute({ key, execute: () => fn(...args), ttlSec }, this.store);
    };
  }
}

// 业务定义工具
const submitRefund = idempotencyMiddleware.wrap(
  (orderId: string, amount: number) => `refund:${orderId}:${amount}`,
  86400,
  async (orderId, amount) => { /* 实际退款 */ },
);

// 业务调用
await submitRefund("DD2026083001", 800);  // 自动幂等
```

## 五、哪些重试是安全的、哪些会双花

这是本题第一个学习要点的核心——答案是**看是否可幂等**。

### 5.1 重试安全清单

| 操作 | 重试安全？ | 原因 |
|------|:---:|------|
| 读操作（GET） | ✅ | 无副作用 |
| LLM 主调用 | ✅ | 天然幂等 |
| 嵌入查询 | ✅ | 无副作用 |
| `upsert` 类写 | ✅ | 设计幂等 |
| 发送 `notification` 通知 | ⚠️ 看是否发重会让人迷路 |
| **付款 / 调用退款** | ❌ | 不幂等会双花 |
| **发邮件 / 推送** | ❌ | 用户收双份 |
| **写唯一索引**（insert） | ⚠️ 加 `ON CONFLICT DO NOTHING` 安全 |
| **触发副作用链** | ❌ | 一处触发多处 |

### 5.2 决策流程

```text
需要重试？
  │
  ├── 是纯读操作？
  │     └── 是 → 直接重试（无需幂等键）
  │
  └── 是写操作？
        │
        ├── 该操作原生幂等（upsert / set-by-key）？
        │     └── 是 → 直接重试
        │
        └── 非幂等？
              │
              ├── 有幂等键基础设施？
              │     └─ 是 → 传幂等键 + 重试
              │
              └── 没基础设施？
                    └── 否 → 不要重试！仅限重试都需该能
```

### 5.3 工具重试的配置矩阵

```typescript
const TOOL_RETRY_POLICY: Record<string, RetryPolicy> = {
  // 纯读
  "query_order":    { maxAttempts: 3, backoff: "exp", idempotent: true },
  "search_docs":    { maxAttempts: 3, backoff: "exp", idempotent: true },

  // 幂等写
  "upsert_user":    { maxAttempts: 2, backoff: "exp", idempotent: true },
  "set_status":     { maxAttempts: 2, backoff: "exp", idempotent: true },

  // 非幂等写：必须带幂等键
  "submit_refund":  { maxAttempts: 1, backoff: "none", idempotent: false, requireIdempotencyKey: true },
  "send_email":     { maxAttempts: 1, backoff: "none", idempotent: false, requireIdempotencyKey: true },
  "create_order":   { maxAttempts: 1, backoff: "none", idempotent: false, requireIdempotencyKey: true },
};
```

**关键原则**：**非幂等写默认不重试**，除非业务显式声明带幂等键。

## 六、与批量、队列的配合

### 6.1 批量调用的限流

批量不是简单加并发——超过上游配额会被全 429：

```typescript
async function batchWithRateLimit<T, R>(
  items: T[],
  batchSize: number,
  maxConcurrentBatches: number,
  fn: (item: T) => Promise<R>,
): Promise<R[]> {
  const semaphore = new Semaphore(maxConcurrentBatches);
  const batches = chunk(items, batchSize);
  return Promise.all(batches.map(async (batch) => {
    await semaphore.acquire();
    try {
      return await Promise.all(batch.map(fn));
    } finally {
      semaphore.release();
    }
  })).then((results) => results.flat());
}

// 示例：批量嵌入 10000 条
batchWithRateLimit(docs, 100, 5, embedDoc);  // 每 100，5 批并发
```

### 6.2 队列化降级

重活不进实时链路，丢进队列异步处理：

```typescript
// 重任务：生成 50 页分析报告
async function handleHeavyTask(req: ReportRequest) {
  // 1. 入队，立即返回「处理中」
  const jobId = await queue.enqueue("heavy_report", req, {
    maxRetries: 3,
    backoff: "exp",
    idempotencyKey: `report:${req.userId}:${req.dateRange}`,
  });

  // 2. 告诉用户去查进度
  return {
    status: "processing",
    jobId,
    pollUrl: `/api/jobs/${jobId}`,
  };
}
```

**好处**：

- 不占实时配额
- 自然削峰填谷
- 失败可重试不阻塞用户

详见[《批量工具调用》](../../Agent开发知识/03-工具调用/05-批量工具调用与并发处理.html)。

### 6.3 与网关的协作

```text
客户端 → 网关 → 上游
          │
          ├── 1. 鉴权 + 限流
          ├── 2. 检测 Retry-After / 429
          ├── 3. 指数退避重试（仅幂等请求）
          ├── 4. 失败进 fallback 链
          └── 5. 重活进队列
```

## 七、端到端落地示例：四周迭代

小智从「偶尔双花」到「幂等基建完备」的 4 周节奏：

| 周 | 任务 | 工具栈 | 完成标准 |
|----|------|--------|----------|
| W1 | 工具清单分级：标哪些可重试，哪些必须幂等 | 内部 wiki | 工具 × 重试策略矩阵 |
| W2 | 幂等基建：SDK + Redis 键 + 失败清除 | 自研中间件 + Redis | 所有非幂等写具需幂等键 |
| W3 | 退避 + 抖动 + Retry-After 尊重 | 全局中间件 | 重试无雪崩 |
| W4 | 演练：双花场景 + 重试风暴 + 错位限流 | runbook + 混沌测试 | 三个月 0 双花事故 |

**四周后的指标**（小智一年内）：

- 双花事故：从年 4 起 → 0 起
- 限流封 IP 次数：年 12 起 → 0 起
- 上游 429 转换率：稳定在 0.3% 以下
