## 〇、贯穿案例：小智的三角取舍史

电商客服「小智」是延迟敏感型（用户等不耐烦会跳走），但代码 Agent「码神」是质量优先型（错一个字符就 build 不过）。三角优先级差极大：

| 产品 | 优先级排序 | 含义 |
|------|-----------|------|
| **小智客服** | 延迟 > 成本 > 质量 | 用户等 3 秒就走，错一点可道歉 |
| **码神助手** | 质量 > 成本 > 延迟 | 用户愿意等，错一个字符 = bug |
| **离线报告生成** | 成本 > 质量 > 延迟 | 跑 1 小时没关系，省 $50 比准 2pp 值 |
| **金融风控** | 质量 > 延迟 > 成本 | 错一次赔千万，延迟可以 5 秒，成本先算了 |

**关键直觉**：三角取舍不是「哪个最重要」，是「**哪个牺牲的代价最小**」。

## 一、三角定义与典型场景偏好

### 1.1 三角的定义

```text
      质量（Quality）
      /\
     /  \
    /    \
   /      \
  /        \
 /__________\
延迟（Latency）  ←→  成本（Cost）
```

- **质量**：任务成功率 / 用户满意度 / 业务指标
- **延迟**：P50 / P95 / P99 响应时间
- **成本**：单次请求 / 月度预算

三者**最多两个能满**，第三个必有所失——这是工程约束，不是技术缺陷。

### 1.2 七类场景的偏好表

| 场景 | 延迟 | 成本 | 质量 | 典型 SLO |
|------|:---:|:---:|:---:|---------|
| **实时客服 / 语音助手** | ★★★ | ★★ | ★ | P95 < 3s，成本 < $0.01/次 |
| **代码补全**（IDE） | ★★★ | ★★ | ★★ | P50 < 500ms，成本 < $0.003/次 |
| **代码 Agent**（码神） | ★ | ★★ | ★★★ | 任成功率 > 80%，成本可控 |
| **离线报告 / 总结** | ★ | ★★★ | ★★ | 月预算固定，质量 > 80% |
| **RAG 问答**（知识库） | ★★ | ★★ | ★★ | P95 < 2s，成本 < $0.005 |
| **金融 / 医疗** | ★★ | ★ | ★★★ | 准确率 > 99%，延迟容忍 5s |
| **内容创作 / 营销** | ★ | ★ | ★★★ | 质量优先，成本延迟不管 |

> ★ 越多越重要。仔细看：所有场景都有「质量」一项——**质量是基线** ，不能为 0。

## 二、六个常见杠杆与边际收益

### 2.1 杠杆一：模型大小（档位）

| 档位 | 延迟 | 成本 | 质量（vs 大模型） |
|------|:---:|:---:|:---:|
| 小模型（mini / 7B） | -50% | -70% | -10~15pp |
| 大模型（4o / Sonnet） | 基线 | 基线 | 基线 |
| 推理模型（o1 / R1） | +500% | +300% | +5~10pp（仅推理任务） |

**边际规律**：从 mini 升到 4o，平均质量 +10pp；从 4o 升到 o1，仅推理任务 +8pp，简单任务 +0pp 甚至 -3pp。

### 2.2 杠杆二：上下文长度

| 长度 | 延迟影响 | 成本影响 | 质量影响 |
|------|:---:|:---:|------|
| 4k | 基线 | 1× | 基线 |
| 32k | +20~40% | +6× | +5~10pp（多文档场景） |
| 128k | +50~80% | +24× | +10pp（长文总结类） |
| 1M | +200% | +192× | 仅「大海捞针」类任务受益 |

**边际规律**：上下文超过任务实际所需 2 倍，质量增益趋零但成本线性涨。

### 2.3 杠杆三：检索 topK + 是否重排

| 策略 | 延迟 | 成本 | 质量（vs baseline） |
|------|:---:|:---:|:---:|
| topK=3, 无重排 | 基线 | 基线 | 基线 |
| topK=10, 无重排 | +30% | +20% | +3~5pp |
| topK=10, 有重排 | +60% | +50% | +8~12pp |
| topK=20, 有重排 | +100% | +100% | +9~13pp（边际递减） |

**边际规律**：topK 从 10→20 通常 +1pp 不到，但延迟 +50%——不划算。

### 2.4 杠杆四：单 Agent vs 多 Agent 协作

| 架构 | 延迟 | 成本 | 质量 |
|------|:---:|:---:|:---:|
| 单 Agent 串行 | 基线 | 1× | 基线 |
| Planner + Executor（双 Agent） | +80% | +2× | +5~15pp |
| 多 Agent 投票（3 个） | +200% | +3× | +8~12pp |
| 多 Agent 辩论 / 反思 | +300% | +4× | +10~20pp |

**边际规律**：多 Agent 适合 **重决策场景**（退款争议、规划），不适合 客服单轮。

### 2.5 杠杆五：是否流式

| 模式 | TTFT（Time-To-First-Token） | 总延迟 | 成本 |
|------|:---:|:---:|:---:|
| 非流式 | 等全部生成完 | 长 | 不变 |
| 流式 | < 500ms | 总长不变，但感知快 | 不变 |

流式对**感知延迟**帮助巨大，但**总耗时**不变。客服 / 长文本生成必上，结构化提取可不上。

### 2.6 杠杆六：缓存

| 缓存类型 | 延迟影响 | 成本影响 |
|----------|:---:|:---:|
| Prompt Cache（服务端） | -10% | -40~85% |
| 语义缓存（客户端） | -90%（命中时） | -90%（命中时） |
| 上下文压缩 | -30~50% | -30~60% |

详见[《Token 成本估算》](02-Token成本估算.html) §4。

## 三、SLO 设定：P95 延迟、单次成本、任务成功率

### 3.1 三类 SLO 的设定方法

**延迟 SLO**：

- 实时交互：P95 < 用户可忍受阈值（通常 2~3 秒）
- 离线任务：P95 < 业务窗口期
- 留 20~30% 余量——99% 才交付 P95 不能用 P95 设上限

**成本 SLO**：

- 月预算 ÷ 月请求量 = 单请求平均成本上限
- 设 P99 单请求成本不超过平均的 **5 倍**（防异常请求烧钱）

**技能 SLO**：

- 业务成功率（任务成功 / 总任务数）——不是「模型通过率」
- 同时跟踪 CSAT（用户满意度）作为兜底

### 3.2 落地示例：SLO 定义

```typescript
interface ProductSLO {
  product: string;
  latency: {
    p50Ms: number;
    p95Ms: number;
    p99Ms: number;
  };
  cost: {
    avgUsdPerRequest: number;
    p99UsdPerRequest: number;
    monthlyBudgetUsd: number;
  };
  quality: {
    taskSuccessRate: number;     // 0~1
    userSatisfaction: number;    // 1~5
  };
}

const XIAOZHI_SLO: ProductSLO = {
  product: "小智客服",
  latency: { p50Ms: 1500, p95Ms: 3000, p99Ms: 5000 },
  cost: { avgUsdPerRequest: 0.005, p99UsdPerRequest: 0.025, monthlyBudgetUsd: 1500 },
  quality: { taskSuccessRate: 0.85, userSatisfaction: 4.3 },
};
```

### 3.3 SLO 监控与违约响应

```text
SLO 状态 → 动作
  ├── 绿色（达成率 > 99%）→ 正常
  ├── 黄色（达成率 95~99%）→ 看监控趋势，准备降级预案
  ├── 红色（达成率 < 95%）→ 立即降级（切小模型 / 关流式 / 限流）
  └── 紫色（达成率 < 90% 持续 1h）→ 紧急回滚到上一稳定版本
```

详见[《可靠性与成本工程》](../../Agent开发知识/13-进阶与工程化/05-可靠性与成本工程.html)。

## 四、客服 vs 代码 Agent 的三角优先级

### 4.1 客服（延迟敏感型）

```text
三角偏好 = 延迟 ≫ 成本 > 质量
```

**理由**：

- 用户等 3 秒就跳走，跳走率 5% 等于收入损失 5%
- 客服回答「差一点」可道歉、可人工兜底
- 单请求成本 $0.01 与 $0.001 都可接受，关键是转化率

**典型优化顺序**：

1. 上流式（TTFT < 500ms）
3. 拆路由：分类 / 提取走 mini，复杂回答走 4o
3. Prompt Caching + 早截断

### 4.2 代码 Agent（质量敏感型）

```text
三角偏好 = 质量 ≫ 成本 > 延迟
```

**理由**：

- 错一个字符 = build 不过 = 用户白等
- 用户已经「等 IDE 跑代码」了，多等 30 秒可接受
- 代码 Agent 单任务 $0.05 与 $0.10 都可接受，关键是能跑通

**典型优化顺序**：

1. 上推理模型（o1 / R1）做复杂规划
2. 多 Agent 投票 / 反思（提升代码正确率）
3. 流式输出用户看着好受（但不优化 TTFT）

### 4.3 对比表

| 维度 | 客服（小智） | 代码 Agent（码神） |
|------|------------|------------------|
| P95 延迟 SLO | 3 秒 | 60 秒 |
| 单任务成本上限 | $0.025 | $0.50 |
| 任务成功率 | 85% | 80% |
| 模型档位 | mini 主 / 4o 备 | 推理模型 o1 必上 |
| 多 Agent 协作 | 否（单 Agent） | 是（必备） |
| 流式 | 是（必备） | 可选 |
| Prompt Cache | 高收益 | 低收益（每次代码不同） |
| 重排 | 低收益 | 低收益 |

## 五、「为了质量无限加 Agent」的反模式

### 5.1 现象

```text
质量只有 75% → 加多 Agent 反思 → 升到 82% → 再加一次辩论 → 升到 85%
→ 但成本涨 4 倍，延迟涨 3 倍，月预算爆
```

**症状**：

- 月预算连月超支
- P95 延迟超 SLO
- 任务成功率涨到顶后再难提升（边际递减）

### 5.2 反模式的四类诱因

| 诱因 | 表现 | 解药 |
|------|------|------|
| **质量 KPI 单一** | 只看成功率，不看成本/延迟 | 设复合 SLO：成功率 × (1 - 成本比) |
| **没有边际记录** | 不知道每多投一档回报多少 | 每次升级必须做「单位成本质量增量」 |
| **局部最优陷阱** | 模型上碰到天花板就开始叠 Agent | 退一步看：是不是 prompt / 数据 / 工具问题 |
| **没设上限** | 不拒绝「再多加一层」的诱惑 | 在 SLO 中设「质量已达上限，禁加 Agent」 |

### 5.3 边际记录表（强制）

每次调杠杆必须更新：

```typescript
interface LeversLog {
  date: string;
  change: string;          // "加 Rerank 模型" / "切到 gpt-4o" / "加反思 Agent"
  deltaQuality: number;    // pp
  deltaLatencyP95: number; // ms
  deltaCost: number;       // USD / 月
  deltaPareto: boolean;    // 是否帕累托改进（无任何维度变差）
  action: "keep" | "rollback";
}

const LOG: LeversLog[] = [
  { date: "2026-08-12", change: "切到 gpt-4o",           deltaQuality: +5,  deltaLatencyP95: +200, deltaCost: +800, deltaPareto: true,  action: "keep" },
  { date: "2026-08-25", change: "加 Rerank",              deltaQuality: +3,  deltaLatencyP95: +300, deltaCost: +180, deltaPareto: true,  action: "keep" },
  { date: "2026-09-05", change: "加 Planner+Executor",    deltaQuality: +8,  deltaLatencyP95: +1500,deltaCost: +600, deltaPareto: false, action: "rollback" }, // 延迟炸
  { date: "2026-09-18", change: "上下文压缩 + 切 mini",   deltaQuality: -1,  deltaLatencyP95: -400,deltaCost: -210, deltaPareto: true,  action: "keep" },
];
```

**关键规则**：任何**非帕累托改动** 必须有强力理由 + 临时灰度 + 回滚预案。

### 5.4 何时该停手

```text
质量 80% → 加 Agent → 84% → 加反思 → 86% → 加辩论 → 87%（+1pp）
↑                              ↑                ↑
成本 -60%， 延迟 -200%        成本 +200%， 延迟 +150%
```

**最后一步明显不划算**——停下来，回到「换 prompt / 数据 / 工具」路径。

## 六、实验方法：改一个旋钮测两边影响

### 6.1 单变量实验法

```text
实验 = 改 1 个旋钮 + 跑 7 天 + 对照组 vs 实验组 + 统计显著性
```

**三个纪律**：

1. **同时只改一个变量**——多变量同时改就无法归因；
2. **固定对照组**——永远把当前生产模型 / 配置跑一遍做基线；
3. **统计显著性**——样本量 < 1000 别下结论。

### 6.2 落地示例：旋钮 A/B 实验

```typescript
interface Experiment {
  knob: string;             // "model" / "topK" / "contextLength" / ...
  baseline: string;         // 当前生产值
  candidate: string;        // 候选值
  metrics: ProductSLO;      // 用 SLO 当成功标准
  minSamples: number;       // 最小样本
  maxDuration: number;      // 最大天数
}

async function runExperiment(exp: Experiment) {
  const baselineResults = [];
  const candidateResults = [];

  // 哈希分桶，5% 流量走候选
  for (const req of trafficFlow) {
    const useCandidate = hashToBucket(req.userId, 100) < 5;
    const result = useCandidate
      ? await runWithConfig(exp.candidate)
      : await runWithConfig(exp.baseline);
    (useCandidate ? candidateResults : baselineResults).push(result);
  }

  if (candidateResults.length < exp.minSamples) return "inconclusive";

  const baseStats = aggregate(baselineResults);
  const candStats = aggregate(candidateResults);

  // 检查是否帕累托改进
  const pareto =
    candStats.quality >= baseStats.quality &&
    candStats.latencyP95 <= baseStats.latencyP95 * 1.05 &&  // 允许 5% 抖动
    candStats.cost <= baseStats.cost * 1.10;                // 允许 10% 抖动

  return {
    baseStats,
    candStats,
    decision: pareto ? "promote" : "rollback",
    reason: pareto ? "all metrics non-worse" : "metric regressed",
  };
}

function aggregate(results: Result[]): ProductSLO["quality"] & ProductSLO["cost"] & ProductSLO["latency"] {
  // ...聚合 P50/P95/avg cost / 成功率
  return { p50Ms: 0, p95Ms: 0, p99Ms: 0, avgUsdPerRequest: 0, p99UsdPerRequest: 0, monthlyBudgetUsd: 0, taskSuccessRate: 0, userSatisfaction: 0 };
}
```

### 6.3 实验记录表

| 实验 | 旋钮 | 基线 | 候选 | Δ 质量 | Δ P95 | Δ 成本 | 帕累托 | 决策 |
|------|------|------|------|:---:|:---:|:---:|:---:|------|
| #1 | 模型 | gpt-4o | claude-sonnet | +3pp | -200ms | +$200 | ✅ | 上线 |
| #2 | topK | 3 | 10 | +2pp | +80ms | +$30 | ✅ | 上线 |
| #3 | topK | 10 | 20 | +0.5pp | +180ms | +$80 | ❌ | 回滚 |
| #4 | 反思 | 单 Agent | + 反思 | +5pp | +1200ms | +$150 | ❌ | 回滚 |

## 七、端到端落地示例：四周迭代

小智从「拍脑袋定档」到「数据驱动的三角优化」的 4 周节奏：

| 周 | 任务 | 工具栈 | 完成标准 |
|----|------|--------|----------|
| W1 | SLO 定义：明确小智的 P95/成本/质量三档 | 内部 wiki | 输出 SLO 文档并通过评审 |
| W2 | 基线测量：跑一周生产数据，对照 SLO | Grafana + LLM 日志 | 拿到每项 SLO 当前达成率 |
| W3 | 旋钮清单 + 边际记录表 | LeversLog | 列出 10+ 旋钮，标边际 |
| W4 | 跑 3 个高优先级实验 | 灰度 + 哈希分桶 | 至少 1 个帕累托改进上线 |

**四周后的指标**（小智 v3 vs v2）：

- P95 延迟：2.4s → 1.6s
- 月成本：$1,740 → $1,230
- 任务成功率：80% → 83%
- 月增实验数：3 个高 ROI 上线
