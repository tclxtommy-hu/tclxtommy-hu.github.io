## 〇、贯穿案例：小智的工单解析闭环

与[《结构化输出》](../01-LLM核心行为/04-结构化输出.html)同一个业务：电商客服「小智」，日 2 万条消息，从用户输入提取结构化工单字段入库。开 `strict: true` 后格式失败率已压到 0.4%，但仍有两个新问题：

1. **中转站多上游**：同一份 schema 打到不同厂商，有的返回 JSON mode（语法合规但字段值编造），有的走工具调用路径返回 `arguments` 字符串——解析路径不统一；
2. **工具调用参数幻觉**：小智升级到 Agent 模式后，模型自主调 `create_ticket`，偶尔参数类型错（`order_id` 传了数字）、甚至把两个工具的参数混在一起。

本文所有方案都围绕这两条线展开。

## 一、解析失败分类

### 1.1 四类失败，一张表看清

修复的第一步不是「试一下能不能修」，而是 **先分类**——不同类别走不同的修复路径，混在一起处理会浪费预算：

| 类别 | 本质 | 典型表现 | 修复路径 |
|------|------|----------|----------|
| **语法失败** | JSON/代码字符串不符合文法 | 尾逗号、单引号、缺右括号、markdown 围栏包裹 | L1 确定性修复（零 token） |
| **结构失败** | 语法合法但不符合 schema | 字段缺失、类型错（string vs number）、枚举值不在白名单 | L2 带错误重试 |
| **语义失败** | 结构合规但内容不可信 | `order_id: "N/A"` 幻觉、`urgency` 与内容矛盾 | 业务校验拦截 → L2 重试 |
| **策略失败** | 模型「选择」了错误行为 | 不调工具、调错工具、提前终止、循环调用同一工具 | 不可盲修 → 见 [五](#五哪些错误不该自动修) |

**关键直觉**：语法失败是「模型手滑」（修复成功率极高），语义失败是「模型无知」（重试可能有效），策略失败是「模型决策」（盲目重试会放大错误）。

### 1.2 落地示例：错误分类器

不要在业务代码里到处 try-catch，写一个统一的分类器，返回结构化的失败原因：

```typescript
import { z } from "zod";

type FailureKind = "syntax" | "schema" | "semantic" | "strategic";

interface ParseFailure {
  kind: FailureKind;
  detail: string;
  repairable: boolean; // false = 直接降级，不进重试
}

function classifyParseError(
  raw: string,
  schema: z.ZodTypeAny,
): ParseFailure {
  // 1) 语法层：JSON.parse 是否通过
  let candidate: unknown;
  try {
    candidate = JSON.parse(raw);
  } catch {
    return { kind: "syntax", detail: "JSON.parse failed", repairable: true };
  }

  // 2) 结构层：schema 校验是否通过
  const result = schema.safeParse(candidate);
  if (!result.success) {
    const first = result.error.issues[0];
    return {
      kind: "schema",
      detail: `${first.path.join(".")}: ${first.message}`,
      repairable: true,
    };
  }

  // 3) 策略层：模型有没有「拒绝回答」或「调错工具」的信号
  const text = typeof candidate === "object" && candidate !== null
    ? JSON.stringify(candidate)
    : String(candidate);
  if (/(cannot|sorry|无法|抱歉)/i.test(text) && schemaTooStrict(schema)) {
    return { kind: "strategic", detail: "model refused or hedged", repairable: false };
  }

  // 语义层需要业务校验，此处返回「结构通过」占位
  return { kind: "semantic", detail: "structure ok, needs business check", repairable: true };
}

function schemaTooStrict(schema: z.ZodTypeAny): boolean {
  // 判断 schema 是否强制所有字段 required 且无 nullable——
  // 过严的 schema 容易逼模型编造或拒答
  return true; // 简化示意，实际按业务 schema 判断
}
```

分类器输出的 `repairable: false` 直接走降级，不进重试池——这就是「避免无限循环」的第一道闸门。

### 1.3 小智实测：分类分布决定修复策略

对小智日均 40 条解析失败（0.4% × 2 万 × 日）做一周分类统计：

| 类别 | 占比 | 修复后成功率 | 结论 |
|------|------|:---:|------|
| 语法失败（围栏/尾逗号） | 58% | 99.8% | L1 修复库可全兜，零 token |
| 结构失败（字段缺失/类型错） | 31% | 84% | L2 带错误重试，最多 2 次 |
| 语义失败（幻觉 order_id） | 9% | 12% | 业务校验拦截后大多转人工 |
| 策略失败（拒答/调错工具） | 2% | 0% | 直接转人工，不重试 |

**洞察**：把修复预算花在语法 + 结构（89% 的失败、修复成功率高）上收益最大；语义和策略失败重试是烧钱。

## 二、自动修复

### 2.1 三层修复手段（按成本升序）

| 层 | 手段 | 成本 | 适用 |
|----|------|------|------|
| L1a | **JSON 修复库**（`jsonrepair` 等） | 毫秒级、零 token | 尾逗号、单引号、缺括号、围栏 |
| L1b | **JSON 抽取**（从混合文本中提取） | 毫秒级、零 token | 输出带解释文字、markdown 围栏、代码块 |
| L2 | **带错误信息重试** | 2 倍 token | L1 修不了的结构/语义缺漏 |

> L0（源头预防：`strict: true` / `guided_json`）见[《结构化输出》](../01-LLM核心行为/04-结构化输出.html) 3.2 节，此处不重复。

### 2.2 JSON 抽取：从混合文本中提取

中转站多上游场景下最常见的问题：模型输出不是纯 JSON，而是「解释文字 + markdown 围栏 + JSON + 尾巴」：

````text
好的，我来帮你创建工单。

```json
{
  "intent": "refund",
  "order_id": "DD2026083001",
  "urgency": "high"
}
```

工单已创建，请问还有其他问题吗？
````

直接 `JSON.parse` 会炸。写一个抽取函数，按优先级尝试三种策略：

````typescript
/** 从混合文本中提取 JSON，按优先级：代码块 > 花括号匹配 > 整体修复 */
function extractJSON(raw: string): unknown {
  // 策略 1：markdown 代码块（```json ... ``` 或 ``` ... ```)
  const fenceMatch = raw.match(/```(?:json)?\s*\n?([\s\S]*?)```/);
  if (fenceMatch) {
    try {
      return JSON.parse(fenceMatch[1].trim());
    } catch { /* 继续尝试 */ }
  }

  // 策略 2：找第一对完整的花括号（处理前后有文字的情况）
  const start = raw.indexOf("{");
  const end = raw.lastIndexOf("}");
  if (start !== -1 && end > start) {
    try {
      return JSON.parse(raw.slice(start, end + 1));
    } catch { /* 继续尝试 */ }
  }

  // 策略 3：jsonrepair 兜底（处理尾逗号、单引号等）
  const { jsonrepair } = require("jsonrepair");
  return JSON.parse(jsonrepair(raw));
}
````

**注意**：策略 2 用 `lastIndexOf` 而不是正则——JSON 里可能有嵌套花括号，正则匹配不到正确的闭合位置。

### 2.3 落地示例：带修复的完整解析管道

把分类器和修复手段串成管道，每一步失败都有明确出口：

```typescript
import { z } from "zod";
import { jsonrepair } from "jsonrepair";

const Ticket = z.object({
  intent: z.enum(["refund", "exchange", "repair", "consult"]),
  order_id: z.string().min(1),
  urgency: z.enum(["low", "medium", "high"]),
});

interface ParseResult<T> {
  ok: boolean;
  data?: T;
  failure?: ParseFailure;
  raw: string;
}

function parseWithRepair<T>(
  raw: string,
  schema: z.ZodType<T>,
): ParseResult<T> {
  // L1a + L1b：抽取 + 修复，零 token
  let candidate: unknown;
  try {
    candidate = extractJSON(raw);
  } catch {
    try {
      candidate = JSON.parse(jsonrepair(raw));
    } catch {
      return {
        ok: false,
        failure: { kind: "syntax", detail: "all extraction failed", repairable: true },
        raw,
      };
    }
  }

  // 结构校验
  const result = schema.safeParse(candidate);
  if (result.success) {
    return { ok: true, data: result.data, raw };
  }

  const issue = result.error.issues[0];
  return {
    ok: false,
    failure: {
      kind: "schema",
      detail: `${issue.path.join(".")}: ${issue.message}`,
      repairable: true,
    },
    raw,
  };
}
```

### 2.4 二次询问的提示词模板

L2 重试的核心是把 **具体的失败原因** 喂回去，而不是笼统地说「输出格式错了」：

```text
你上次输出的 JSON 未通过校验：

错误：order_id: Expected string, received number
原始输出：{"intent": "refund", "order_id": 2026083001, "urgency": "high"}

请修正上述错误，重新输出完整 JSON。注意：
1. 只输出 JSON，不要包含任何其他文字或 markdown 围栏
2. order_id 必须是字符串类型
3. 不要省略任何字段
```

**要点**：

- **只指出本次错误**，不要把全部 schema 重贴（浪费 token 且模型可能「过度修正」改对的部分）；
- **附上原始输出**，让模型做 diff 而不是从头重写；
- **用祈使句列出具体修改要求**，不要说「请注意格式」。

## 三、重试预算与模型切换

### 3.1 重试预算设计

「避免无限循环」不是靠「最多重试 3 次」一句话，而是 **三个维度的预算同时收紧**：

| 维度 | 预算 | 触发动作 |
|------|------|----------|
| **次数** | 同一错误最多重试 2 次 | 耗尽 → 降级 |
| **token** | 重试消耗 ≤ 原始调用的 1.5 倍 | 超支 → 降级 |
| **时间** | 重试总耗时 ≤ 5 秒（实时场景 ≤ 2 秒） | 超时 → 降级 |

三个维度任一耗尽都立即降级， **不是全耗尽才降**。

### 3.2 落地示例：带预算的重试循环

```typescript
import type { ZodType } from "zod";

interface RetryBudget {
  maxAttempts: number;
  maxExtraTokens: number; // 重试允许额外消耗的 token 上限
  maxTotalMs: number;
}

const DEFAULT_BUDGET: RetryBudget = {
  maxAttempts: 2,
  maxExtraTokens: 1500,
  maxTotalMs: 5000,
};

async function parseWithBudget<T>(
  call: (messages: unknown[]) => Promise<{ raw: string; tokens: number }>,
  schema: ZodType<T>,
  budget: RetryBudget = DEFAULT_BUDGET,
): Promise<T> {
  const startAt = Date.now();
  let extraTokens = 0;
  const messages: unknown[] = [];

  for (let attempt = 0; attempt <= budget.maxAttempts; attempt++) {
    // 预算检查：任一超支立即降级
    if (extraTokens > budget.maxExtraTokens) throw new BudgetExhausted("token");
    if (Date.now() - startAt > budget.maxTotalMs) throw new BudgetExhausted("time");

    const { raw, tokens } = await call(messages);
    extraTokens += tokens;

    const result = parseWithRepair(raw, schema);
    if (result.ok) return result.data!;

    const failure = result.failure!;
    if (!failure.repairable) throw new UnrepairableError(failure);
    if (attempt === budget.maxAttempts) throw new BudgetExhausted("attempts");

    // 构造修复提示
    messages.push(
      { role: "assistant", content: raw },
      { role: "user", content: repairPrompt(raw, failure.detail) },
    );
  }

  throw new BudgetExhausted("unreachable");
}

class BudgetExhausted extends Error {
  constructor(public dimension: string) {
    super(`Retry budget exhausted: ${dimension}`);
  }
}

class UnrepairableError extends Error {
  constructor(public failure: ParseFailure) {
    super(`Unrepairable: ${failure.kind} - ${failure.detail}`);
  }
}

function repairPrompt(rawOutput: string, errorDetail: string): string {
  return `你上次输出的 JSON 未通过校验。\n\n错误：${errorDetail}\n原始输出：${rawOutput}\n\n请修正后重新输出完整 JSON。只输出 JSON，不要包含其他文字。`;
}
```

**关键设计**：`BudgetExhausted` 和 `UnrepairableError` 是两种不同的异常——前者交给上层决定「换模型重试还是降级」，后者直接降级（因为换了模型也修不了策略性错误）。

### 3.3 模型切换策略

重试失败后，下一步是「切一个更强的模型再试一次」还是「直接降级」？按错误类别决策：

| 错误类别 | 切模型重试？ | 理由 |
|----------|:---:|------|
| 语法失败（L1 修不了） | ✅ 换 **同价位** 模型 | 可能是当前模型 tokenizer 或训练数据问题 |
| 结构失败（字段/类型错） | ✅ 换 **更强** 模型 | 复杂 schema 小模型理解不了，升级一档可能就好 |
| 语义失败（幻觉） | ⚠️ 谨慎 | 换更强模型能减少幻觉，但不能根除；先看业务校验能否兜住 |
| 策略失败（拒答/调错） | ❌ 不切 | 换模型可能引入新的策略错误，且成本不可控 |

**切模型次数上限**：1 次。小智的规则是「gpt-4o 失败 → gpt-4o + strict 重试 → 仍失败 → claude-sonnet 重试 1 次 → 仍失败 → 转人工」，全链路最多 3 次 LLM 调用。

### 3.4 小智实测：预算对成本的影响

| 策略 | 日均失败数 | 日均重试 token | 日均 LLM 成本 | 人工介入 |
|------|:---:|:---:|:---:|:---:|
| 无预算无限重试 | 40 → 8 | 120k | $0.72 | 8 条 |
| 预算制（本文方案） | 40 → 12 | 38k | $0.23 | 12 条 |

预算制多 4 条转人工（$0.20 人力），但每天省 $0.49 token 费 + 消除了重试风暴风险。 **结论**：解析修复不是「修复率越高越好」，而是「预算内修复率最大化」。

## 四、与结构化输出、工具调用的衔接

### 4.1 三条解析路径，一个入口

Agent 场景下，模型输出可能走三条路径，解析入口必须统一：

```text
模型返回
  ├── content 字段有 JSON → 走 parseWithRepair（本文 L1 + L2）
  ├── tool_calls 字段有参数 → 走 parseToolCallArgs（下节）
  └── 两者都为空 → 策略失败（模型没按预期行动）
```

统一入口的好处：修复预算、分类统计、告警都只写一份。

### 4.2 工具调用参数的解析与修复

工具调用的参数是 **字符串形式的 JSON**（`function.arguments`），解析失败的表现和 `content` 字段不同：

```typescript
import type { ChatCompletionMessageParam } from "openai/resources/chat/completions";

interface ToolCallParseResult {
  ok: boolean;
  toolName?: string;
  args?: Record<string, unknown>;
  failure?: ParseFailure;
}

function parseToolCall(
  message: ChatCompletionMessageParam & { tool_calls?: unknown[] },
  expectedTool: string,
  argsSchema: ZodType,
): ToolCallParseResult {
  const calls = message.tool_calls ?? [];

  // 情况 1：模型没调任何工具 → 策略失败
  if (calls.length === 0) {
    return {
      ok: false,
      failure: { kind: "strategic", detail: "no tool call returned", repairable: false },
    };
  }

  // 情况 2：调了但调错工具 → 策略失败
  const call = calls[0] as { function: { name: string; arguments: string } };
  if (call.function.name !== expectedTool) {
    return {
      ok: false,
      failure: {
        kind: "strategic",
        detail: `expected ${expectedTool}, got ${call.function.name}`,
        repairable: false,
      },
    };
  }

  // 情况 3：调对了但参数解析/校验失败 → 语法或结构失败
  const result = parseWithRepair(call.function.arguments, argsSchema);
  if (result.ok) {
    return { ok: true, toolName: expectedTool, args: result.data };
  }
  return { ok: false, failure: result.failure };
}
```

**注意**：`parseWithRepair` 是同一个函数——工具参数和 content 字段的修复逻辑完全复用，这就是统一入口的意义。

### 4.3 多工具并行调用时的参数混淆

模型一次返回多个 `tool_calls` 时，参数可能互相污染（`searchOrders` 的参数混进 `searchUsers`）。防御方式：

1. **每个工具的 schema 独立校验**，不要校验「合并后的参数集」；
2. **参数字段名加工具前缀**（如 `searchOrders_query` vs `searchUsers_query`）——但会增加 token，仅在混淆率 > 3% 时考虑；
3. **更根本的方案**：拆分为多轮调用，每轮只允许调一个工具（配合 `tool_choice: "required"`）。小智从并行多工具改为一轮一工具后，参数混淆从 2.1% 降到 0%。

## 五、哪些错误不该自动修

这是本文最重要的一节。 **不是所有解析失败都应该重试**——盲目重试会把小问题放大成事故。

### 5.1 直接失败清单

| 信号 | 为什么不修 | 正确动作 |
|------|-----------|----------|
| 输出包含「我无法」「抱歉」「作为 AI」 | 模型主动拒绝——重试只是换一种方式拒绝 | 转人工或调整系统提示 |
| `tool_calls` 为空（Agent 模式） | 模型选择不调工具——这是决策，不是格式错误 | 检查提示词 / schema 是否过严 |
| 连续 3 次同样错误 | 修复提示词没有生效——重试第 4 次也不会生效 | 告警 + 冻结重试 |
| 输出长度为 0 或只有空白 | 可能是内容安全过滤——重试会反复触发 | 记录日志 + 降级 |
| 幻觉的 `order_id` 查库不存在 | 业务级错误——模型不知道真实订单号，重试只会编另一个 | 拆两步：先查订单列表让模型选 |
| 重试后输出与上次完全相同 | 模型陷入确定性循环——temperature > 0 也不管用 | 直接降级 |

### 5.2 落地示例：直接失败判定

```typescript
function shouldSkipRetry(
  failure: ParseFailure,
  raw: string,
  attemptHistory: string[],
): boolean {
  // 规则 1：策略失败不重试
  if (failure.kind === "strategic") return true;

  // 规则 2：连续相同错误不重试
  if (attemptHistory.length >= 2) {
    const lastTwo = attemptHistory.slice(-2);
    if (lastTwo[0] === lastTwo[1]) return true;
  }

  // 规则 3：空白输出可能是内容过滤
  if (raw.trim().length === 0) return true;

  // 规则 4：拒答信号
  if (/(我无法|抱歉，作为|I cannot|I'm sorry, as an AI)/i.test(raw)) return true;

  return false;
}
```

**底线原则**：解析修复闭环的目标是「把格式问题自动化消化」，不是「把业务问题自动化掩盖」。该转人工的转人工，该修 schema 的修 schema。

## 六、端到端落地示例：四周迭代

以小智从 v1（纯提示词）升级到 v2（解析闭环）为例：

| 周 | 任务 | 工具栈 | 完成标准 |
|----|------|--------|----------|
| W1 | 分类统计：收集 7 天解析失败样本，跑分类器打标 | zod + 自写 classifyParseError | 输出四类占比表 |
| W2 | L1 修复管道：extractJSON + jsonrepair 接入解析入口 | jsonrepair、zod | 语法失败修复率 ≥ 99% |
| W3 | L2 重试 + 预算：带预算的重试循环 + 拒答拦截 | OpenAI SDK + zod | 重试成功率 ≥ 80%，零无限循环 |
| W4 | 监控告警：失败率看板 + 分类占比周报 + 熔断 | Grafana / 告警 webhook | 失败率 > 2% 自动告警 |

**四周后的指标**：

- 格式失败率：6.2% → 0.05%
- 日均转人工：约 10 条
- 重试成本占比：≤ 3%（总 LLM 成本）
- 解析 **P99** /ˌpiː ˈnaɪn tiː naɪn/ （ **99th Percentile** ，第 99 百分位数）延迟增加：≤ 800ms（含重试）
