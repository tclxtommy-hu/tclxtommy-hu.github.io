## 〇、贯穿案例：小智的「离线 96 分，线上翻车」

沿用 [《Prompt Injection 深挖》](01-Prompt-Injection深挖.html) 的电商客服「小智」。v2.1 上线前：

- 离线黄金集 500 题，**综合分 96.4**，通过所有门禁；
- 灰度 10% 第 2 天，业务反馈：**「看起来答得对，但用户都在重复问同样的问题」**；
- 抽样看，**真实问题分布**与黄金集严重不一致——黄金集 70% 是「退货流程」「怎么退款」，线上 70% 是「订单还没到怎么办」「物流不更新」「发票问题」；
- 模型的「物流不更新」回复里，有 12% 的幻觉（说「已为您催件」但实际没调任何工具）。

离线 96 分，线上 CSAT 反而跌到 3.5。

根因：

1. 黄金集**严重过期**——构建于 v1.2，上线 v2.1 时 6 个月没更新；
2. 黄金集**没覆盖真实长尾**——只覆盖高频 30 个问题；
3. 离线断言**没判「是否真的调工具」**——幻觉在断言外；
4. **没有在线采样回灌**——黄金集与生产分布漂移半年无人发现。

本文围绕「怎么避免这类翻车」展开。

## 一、为什么离线高分线上仍翻车：评测的本质是分布问题

### 1.1 离线评测的三个隐含假设

离线评测跑分的过程，本质是：

```
sample (from a fixed set) → 模型 → 输出 → 断言 → 分
```

它隐含了三个假设：

1. **黄金集 ≈ 真实分布**——评测用的样本能代表线上；
2. **断言 ≈ 真实标准**——自动判分能替代人；
3. **一次跑分 ≈ 长期表现**——一个版本的分数能代表未来 N 周。

三个假设任何一个错位，都会「离线高分线上翻车」。

### 1.2 三种典型错位

| 错位 | 后果 | 典型场景 |
+|------|------|-----------|
| **分布漂移** | 离线高分但线上答非所问 | 业务变更 / 季节 / 新功能上线后 |
| **断言盲区** | 离线高分但线上触红线 | LLM-as-judge 不知红线 / 黑名单未覆盖 |
| **单次不可靠** | 离线高分但下个版本就翻 | 模型温度波动 / 抽样过少 |

> 实测：小智 v1.4 → v2.1 6 个月，黄金集与生产分布的 KL 散度从 0.21 漂到 **0.78**——完全失去代表性。

### 1.3 离线 vs 在线：各自的强项与盲区

| 维度 | 离线评测 | 在线评测 |
|------|----------|----------|
| **速度** | 5 分钟跑 100 题 | N 天看到 N 题真实 |
| **成本** | 低（一次性调用） | 高（生产流量占用） |
| **覆盖** | 可枚举 | 真实但稀疏 |
| **代表** | **可老化** | **实时代表** |
| **判分** | 自动断言 | 需人标 / 用户行为 |
| **作用** | **门禁 / 回归** | **发现 / 漂移** |

> 一句话总结：**离线决定「能不能发」，在线决定「发了之后发生了什么」**。

## 二、离线评测：黄金集、回归、断言与 LLM-as-judge 的坑

### 2.1 黄金集的构成

一份健康的黄金集 = 5 类样本：

| 类型 | 占比 | 作用 |
|------|------|------|
| **高频真实问题** | 40% | 主力问题，覆盖业务量大的 |
| **低频真实问题** | 30% | 长尾覆盖 |
| **历史坏例** | 15% | 历史上出过的错，防回归 |
| **对抗样本** | 10% | 见 [01 篇](01-Prompt-Injection深挖.html)，防注入 |
| **断言陷阱** | 5% | `not_contains` / `must_contain` 反例，防断言盲区 |

> 总数 < 500 不可信，> 2000 收益递减。**关键是比例与新鲜度，不是绝对数量**。

### 2.2 黄金集「四新鲜」原则

| 维度 | 多长必须刷新 | 谁负责 |
+------|--------------+--------|
| **样本新鲜** | 每月 +10% | 产品 + 算法 |
| **断言新鲜** | 每月 1 次 | 算法 |
| **真实抽样回灌** | 每周 | 算法 + 标注 |
| **历史坏例回灌** | 实时 / 每日 | 运营 + 算法 |

> 小智 v2.1 翻车的根因：六个月没刷新，**真实抽样回灌为零**——黄金集完全与生产脱节。

### 2.3 断言设计：三层断言

```typescript
// assertion.ts —— 三层断言设计
interface Assertion { kind: "exact" | "regex" | "judge"; score: number; weight: number }
interface Case { id: string; query: string; expected?: string; assertions: Assertion[] }

// 三层断言：
// 1) 精确/正则（30% 权重）：硬指标（订单号格式、退款金额一致性）
// 2) LLM-as-judge（50% 权重）：语义/风格/忠实度
// 3) 工具调用断言（20% 权重）：是否真的调了、参数对不对

export function buildAssertions(c: Case): Case {
  c.assertions = [
    // 第一层：硬指标
    { kind: "regex", score: 0, weight: 0.3, pattern: /订单号\s*\d{8,}/ },
    // 第二层：LLM-as-judge
    { kind: "judge", score: 0, weight: 0.5, prompt: "判断回复是否准确回应用户问题，0/1 打分" },
    // 第三层：工具调用
    { kind: "exact", score: 0, weight: 0.2, expectedToolCalls: ["query_order"] },
  ];
  return c;
}
```

> 关键：**硬指标永远比 LLM-as-judge 优先**——前者是「确定的事实」，后者是「主观打分」。

### 2.4 LLM-as-judge 的「五不准」

LLM-as-judge 是把双刃剑——用得不好比不用更危险：

| 不准 | 后果 |
+------|------|
| 1. **不准唯一** | 不能让它替代所有断言，必须和硬指标、工具断言并用 |
| 2. **不准黑盒** | 必须能解释「为什么这个分」，否则回归难定位 |
| 3. **不准用同源模型** | 不能用同一个模型既当选手又当裁判（自评偏置） |
| 4. **不准静态 prompt** | 每季度重测一致率，漂移 > 5% 必须重训 |
| 5. **不准替代人工抽检** | 每月至少 200 条人工抽检作为锚点 |

补充（Python，LLM-as-judge 一致率自检）：

```python
from sklearn.metrics import cohen_kappa_score
# judge_self_check.py —— 季度自检脚本
def judge_consistency(labels_a, labels_b):
    return cohen_kappa_score(labels_a, labels_b)
# 实战：gpt-4o-mini 自身一致率 0.81、与人工 kappa 0.74
# 阈值：< 0.7 必须重训 prompt 或换模型
```

### 2.5 LLM-as-judge 使用准则

1. **温度必须为 0**——否则同样问题不同分；
2. **结构化输出**——必须返回 JSON 分数 + 理由；
3. **每季度重测**一致率——每月 100 题同标复测；
4. **多模型投票**——高风险类目用 2–3 个裁判投票。

```typescript
// llm-judge.ts
export async function llmJudge(query: string, response: string): Promise<{ score: number; reason: string }> {
  const r = await openai.chat.completions.create({
    model: "gpt-4o-mini",
    temperature: 0,
    response_format: { type: "json_object" },
    messages: [
      { role: "system", content: "你是评测员，对回复打分 0-1，必须返回 JSON { score, reason }" },
      { role: "user", content: `问题: ${query}\n回复: ${response}` },
    ],
  });
  return JSON.parse(r.choices[0].message.content);
}
```

## 三、在线评测：采样偏差、影子流量、人机协同与告警

### 3.1 在线评测的三件事

| 维度 | 做什么 | 频率 | 谁负责 |
|------|--------|------|--------|
| **采样标注** | 生产对话抽样人工标 | 每周 200 条 | 标注 + 算法 |
| **影子流量** | 新模型并行打分但不返回 | 灰度期间 | 算法 |
| **实时告警** | 关键指标异常立刻告警 | 实时 | 运维 |

### 3.2 影子流量：新模型并行打分

主示（Node.js + TS）：

```typescript
// shadow-eval.ts —— 影子流量打分，不影响用户
export async function shadowScore(
  query: string, prodAnswer: string,
  prodMeta: { promptVersion: string; modelVersion: string },
  candidate: { promptVersion: string; modelVersion: string },
): Promise<void> {
  // 1) 候选模型跑（用户不感知）
  const candAnswer = await callCandidate(query, candidate);

  // 3) 计算差异（仅记录，不影响用户）
  const diff = {
    prodAnswer, candAnswer,
    bleu: similarity(prodAnswer, candAnswer),      // 文本相似度
    judgeScore: await llmJudge(query, candAnswer),
  };
  await db.shadowEval.create({ query, prodMeta, candidate, diff });
}
```

> 关键：**影子流量必须不返回给用户**——任何返回都是改变了用户体验，影响 A/B 真实性。

### 3.3 采样偏差的三类与对策

| 偏差 | 现象 | 对策 |
|------|------|------|
| **热度偏差** | 高频问题过度代表 | 采样权重按业务量反比加权 |
| **时间偏差** | 业务季节 / 活动期 | 月度刷新基线，季度重标 |
| **用户分层偏差** | VIP / 普通用户分布不一致 | 按用户分层采样，VIP 单独评 |

主示例（Node.js + TS，分层采样）：

```typescript
// stratified-sample.ts
export async function sampleConversations(opts: { total: number; strata: Record<string, number> }) {
  // 按用户层级 / 业务线 / 风险类目分层
  const samples = [];
  for (const [stratum, pct] of Object.entries(opts.strata)) {
    const n = Math.floor(opts.total * pct);
    const s = await db.conversation.aggregateSample({
      where: { stratum }, take: n, orderBy: { random: true },
    });
    samples.push(...s);
  }
  return samples;
}
```

### 3.4 人机协同：标多少、怎么标、标多久

| 阶段 | 人工标注量 | 频率 |
|------|------------|------|
| **黄金集构建期** | 1500+  | 一次性 |
| **日常运营期** | 每周 200 条 | 每周 |
| **灰度期** | 每日 100 条 | 每日 |
| **告警触发后** | 200 条/次 | 事件驱动 |

> **「每周 200 条」是黄金数字**——再少发现不了漂移，再多成本不可持续。

### 3.5 在线告警：哪些指标必须实时告警

| 指标 | 阈值 | 告警级别 |
+------|------|----------|
| **幻觉率** | > 5%（24h 滑动） | P2 |
| **拒答率** | > 30% | P2 |
| **CSAT** | < 3.5 | P1 |
| **S1 触发** | > 0 | P0 |
| **TTFT P99** | > 3s | P2 |
| **成本/会话** | > 预算 150% | P2 |

> 告警必须 **带 actionable 信息**：不只是「幻觉率高了」，而是「近 24h 物流类目幻觉率 8%，命中订单号 5xxxx，prompt v2.1」。

## 四、评测工具与框架：Ragas / DeepEval / PromptFoo 的选型

### 4.1 三家框架对比

| 框架 | 强项 | 弱项 | 适合 |
|------|------|------|------|
| **PromptFoo** | YAML 用例，**CI 友好** | RAG 指标弱 | 通用回归、CI 接入 |
| **DeepEval** | 多指标框架，断言丰富 | 学习曲线陡 | 评测驱动开发 |
| **Ragas** | **RAG 专指标**（faithfulness / answer_relevancy） | 非 RAG 场景弱 | RAG 系统 |
| **自研 + pytest** | 完全可控 | 维护成本 | 大团队、有专门平台 |

> 实测组合：**PromptFoo（通用 + CI）+ Ragas（RAG 专用）+ 自研（业务断言）** 是最常见搭配。

### 4.2 Ragas 的关键指标

```python
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision

result = evaluate(
    dataset,           # 包含 question / answer / contexts / ground_truth
    metrics=[faithfulness, answer_relevancy, context_precision],
)
# 关键指标：
#   - faithfulness 0.91：回答是否与检索段一致
#   - answer_relevancy 0.87：回答是否与问题相关
#   - context_precision 0.83：检索段是否精准
```

> 注意：**Ragas 指标只信相对值**——同一数据集上 A 模型 0.92 vs B 模型 0.85 才有意义；绝对值 0.92 与别人家比没意义。

### 4.3 落地示例：PromptFoo CI 集成

```yaml
# promptfooconfig.yaml —— 接入 CI
prompts:
  - file://prompts/system.txt
providers:
  - id: openai:gpt-4o-mini
tests:
  - file://corpus/golden.yaml    # 黄金集
  - file://corpus/redteam.yaml   # 红队集
assert:
  - type: contains
    value: bestätigen   # 包含"已确认"
  - type: not-contains
    value: 风险标记     # 不能包含「风险标记」
  - type: javascript
    value: output.includes("订单") && output.length < 200
```

> 关键：**断言必须能 fail**——红绿灯太宽容 = 没跑过。

## 五、端到端落地示例：四周闭环小智评测体系

### 5.1 四周排期

把本文所有零件排成四周（1 算法 + 1 工程兼标注）：

| 周 | 动作 | 产出 | 指标变化 |
| ---- | ------ | ------ | ---------- |
| W1 | 重构黄金集（1200 题，按 5 类比例）；硬指标断言覆盖；CI 接入 PromptFoo | 黄金集 v3 + CI | 离线门槛稳 |
| W2 | 接入 Ragas（RAG 三个指标）；LLM-as-judge 一致率季度自检 | Ragas + 评分器 | RAG 评测覆盖 |
| W3 | 影子流量框架（候选模型并行打分）；采样偏差分层修复 | 影子打分 | 上线决策变可靠 |
| W4 | 实时告警面板（6 指标）；告警带 actionable 信息 | 告警系统 | 漂移 1 天内可见 |

### 5.2 工具栈

| 环节 | 工具 | 备注 |
+|------|------|------|
| 黄金集 | PostgreSQL + 后台 | 按类 / 严重度管理 |
| 离线断言 | PromptFoo + 自研 JS 断言 | CI 集成 |
| RAG 指标 | Ragas | 每周跑分 |
| LLM-as-judge | gpt-4o-mini（温度=0，结构化输出） | 季度自检 |
| 影子流量 | 自研 + Kafka | 灰度期间并行 |
| 标注 | Label Studio | 每周 200 条 |
| 告警 | ClickHouse + Grafana + Alertmanager | 6 指标带 actionable |

## 自检清单

- [ ] 黄金集按 5 类比例（高频 / 长尾 / 历史坏例 / 对抗 / 陷阱），总 500–2000 题；
- [ ] 黄金集每月 +10%、断言每月 1 次、真实抽样每周回灌；
- [ ] 三层断言（硬指标 / LLM-as-judge / 工具调用），硬指标永远优先；
- [ ] LLM-as-judge 满足「五不准」（不唯一 / 不黑盒 / 不同源 / 不静态 / 不替代人工）；
- [ ] LLM-as-judge 温度=0、结构化输出、季度一致率自检 ≥ 0.7；
- [ ] 在线采样按 **用户分层 / 业务线 / 风险类目**，热度反比加权；
- [ ] 影子流量并行打分但**不返回用户**；
- [ ] 每周 200 条人工标注进周报，灰度期每日 100 条；
- [ ] 6 指标（幻觉率 / 拒答率 / CSAT / S1 / TTFT / 成本）实时告警，告警带 actionable；
- [ ] PromptFoo 接 CI、Ragas 跑 RAG、自研跑业务断言三轨并行；
- [ ] **离线决定发不发，在线决定发了之后看到了什么**——两者独立看、不互相替代。
