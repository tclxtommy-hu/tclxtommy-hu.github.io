## 〇、贯穿案例：小智的「风控过度」

沿用 [《Prompt Injection 深挖》](01-Prompt-Injection深挖.html) 的电商客服「小智」v1.4，护栏已经成型。但运营两个月后出现了一个意料之外的问题：

- 业务方投诉：「小智对「帮我把钱退到 XX」类合理请求**也走人工**，CSAT 反而从 4.3 降到 3.7」
- 客服主管翻日志：「上月 2.4% 用户被路由到人工，其中 38% 是误杀——'我想退订'被拦成了'违规操作'」
- 数据组发现：「拦截命中与命中降幅**没有进入产品周报**——只有 'S1 触发数' 在告警里，'误杀率' 完全没量」

这就是 **「护栏没产品化」的典型症状**：

1. 策略写在代码里、if-else 散落 5 个服务、调阈值要发版；
2. 拦截命中可看，但 **误杀率不可看** —— 因为没有回查链路；
3. 第三方 Moderation API 切换时才发现**策略全部耦合**，换要半年；
4. **没有策略灰度**，某条新策略线上引发 20% 误杀后才知道——但已经伤了 CSAT。

抽样 1000 条人工会话，得到护栏 v1.4 的真实运营基线：

| 指标 | 数值 |
|------|------|
| 总拦截数 | 218 / 1000（21.8%） |
| 其中真违规（S1/S2） | 41 / 1000（4.1%） |
| **误杀（实际可放行）** | **177 / 1000（17.7%）** |
| 误杀率 | **81.2%** |
| 误杀带来的 CSAT 损失 | -0.6 (4.3 → 3.7) |

本文围绕「把这 177 条误杀降到 30 条以内」展开。

## 一、护栏是什么：四类与三种「集中地」

### 1.1 护栏四类

工程上任何一道护栏都落在下面四类之一（或组合）：

| 类 | 检测对象 | 典型规则 | 小智举例 |
|----|----------|----------|----------|
| **主题限制**（Topical） | 离题 / 越界 / 业务外 | 「不聊政治」「不答医学」 | 用户：「我得了 XX 病能吃这个药吗？」→ 拒答 |
| **PII / 合规**（Privacy） | 个人信息、机密数据 | 手机号、身份证、订单明文外发 | 输出包含「订单号 12345678」→ 脱敏 |
| **内容安全**（Harmful） | 仇恨、歧视、暴力、性 | 第三方分类器 + 正则 | 用户辱骂 → 不回应辱骂 |
| **越狱 / 注入**（Jailbreak） | Prompt Injection、角色劫持 | 见 [01 篇](01-Prompt-Injection深挖.html) | 「忽略指令」类 |
| **工具权限**（Tool ACL） | 工具调用是否符合最小权限 | 白名单 + 参数范围 | 模型尝试调 `grant_role('admin')` → 拦截 |

> 注意：**「PII 合规」和「内容安全」必须分开做**——同一段文本可能一个要「脱敏保留」一个要「直接拒答」，规则混在一起会互相打架。

### 1.2 三种「集中地」

散落的 if-else 不可维护。护栏必须 **集中在一个服务**——三种实现路径：

| 路径 | 适合谁 | 优点 | 缺点 |
|------|--------|------|------|
| **代码内集中** | 单业务线、单团队 | 简单、快 | 无法跨业务复用、无法策略灰度 |
| **护栏 SDK** | 多业务线、同一语言 | 一次升级全员收益 | 必须升级版本才生效、不利于策略热更新 |
| **护栏中台（推荐）** | 公司级、多业务线、多语言 | **可配置、观测、可版本化、可灰度** | 初期投入大 |

> 小智 v1.5 走的是「护栏中台」路径——下面所有设计都基于这个前提。

## 二、同步拦截 vs 异步审核：何时快、何时准

### 2.1 同步 vs 异步

| 维度 | 同步拦截 | 异步审核 |
|------|----------|----------|
| 时机 | 请求 **返回前** 完成 | 请求 **返回后** 后台跑 |
| 时延 | 必须 < 整体时延的 20% | 不影响用户体验 |
| 准确率 | 通常 7090%（快模型） | 可上 90–98%（慢模型/多模型投票） |
| 动作 | 改写 / 拒答 / 降级 | 告警 / 人工复审 / 撤桶 |
| 适合 | 主流业务对话、用户可感知 | 高风险垂类、审计可接受延迟 |

### 2.2 场景决策表

| 场景 | 同步？ | 理由 |
|------|--------|------|
| 客服 Bot 普通问答 | 是 | 用户在等，必须给 |
| 投资建议 / 医疗建议 | 否 | 答错成本高，宁可异步审核 |
| 内批量摘要 | 否 | 用户不感知，全异步 |
| 客服高风险垂类（退款、投诉） | **混合** | 同步拦 PII/越狱，异步复审合规口径 |
| RAG 内部知识问答 | 是 | 快、不在公网 |

> 小智 v1.4 → v1.5 把「投资/医疗/政策外承诺」从同步改异步，**同步误杀率立刻降 12 个百分点**。

### 2.3 落地示例：同步 / 异步编排（Node.js + TS）

```typescript
// moderation-orchestrator.ts —— 同步拦截 + 异步复审双层
type Decision = "pass" | "rewrite" | "reject" | "human" | "audit";

export async function moderate(
  input: { query: string; response: string; ctx: { tenant: string; riskClass: string } },
): Promise<{ decision: Decision; safeResponse: string }> {
  // 1) 同步层（< 80ms）：规则 + 小判分器
  const sync = await syncCheck(input);
  if (sync.decision === "reject") {
    return { decision: "reject", safeResponse: sync.safeReply };
  }

  // 2) 异步层（后台）：大模型/多模型投票
  enqueueAudit({
    input, syncResult: sync,
    onResult: (async) => {
      if (async.decision === "violation") {
        recordMetric("post_audit_violation", 1);
        // 已经发出去的回复：走"撤回 + 人工接管"流程
        triggerRecall(async.conversationId, async.reason);
      }
    },
  });

  // 3) 同步放行 + 异步审核同时进行
  return { decision: sync.decision, safeResponse: sync.safeText ?? input.response };
}
```

关键：**异步审核命中后的「撤回 + 接管」流程必须有**——否则异步没意义。

## 三、护栏应放在模型前、后，还是工具层

### 3.1 三层各自的边界

| 层 | 检测对象 | 能拦什么 | 拦不住什么 | 性能成本 |
|----|----------|----------|------------|----------|
| **模型前**（Pre-LLM） | 用户输入、检索段 | 明显的越狱、敏感词、长度异常 | 间接注入、伪装指令、跨段语义攻击 | < 30ms |
| **模型后**（Post-LLM） | 模型输出 | 风格串味、违规内容、外发意图 | 已发生的工具调用、业务已发生的副作用 | 50–200ms |
| **工具层**（Tool Gate） | 工具调用 | 实际的下单 / 外发 / 改权限 | 文本输出里的内容问题 | 10–50ms |

> 误判成本：**模型前 > 模型后 > 工具层**——越往后越接近业务「真的发生了」，误判成本越高。所以工具层必须是 **白名单 + 业务校验** 的最后一道。

### 3.2 不要混层

常见错误：「把工具权限校验放进 model 前判分器」。后果：

- 模型前判分器成了业务高耦合点；
- 调一次业务校验要重启模型服务；
- 跨业务复用难。

原则：**工具层永远独立**，甚至**别**走主 LLM 服务的代码库。

### 3.3 三层架构总成图

```mermaid
flowchart LR
  Q[用户输入] --> Pre[Pre-LLM 闸门<br/>越狱/敏感词/限长]
  Pre --> R[检索]
  R --> LL[M[LLM 生成]]
  LL --> Post[Post-LLM 闸门<br/>风格/外发意图/PII]
  Post --> Tool[工具闸门<br/>白名单+Schema+业务校验]
  Tool --> S[侧效应: 退款/外发/...]
```

> **三层都拦的不是同一类问题**——三层是「不同类问题的不同拦截位」，必须都上。

## 四、误杀与漏放的运营：阈值、抽样、撤桶

### 4.1 「拦截命」不是单一指标

一个被拦的对话，必须能回答：拦的对不对？怎么回查？谁改的策略？上线后发生了什么变化？四个问题对应四类指标：

| 指标 | 定义 | 何时看 |
|------|------|--------|
| **拦截率** | 被拦对话 / 总对话 | 趋势监控（突增突降都告警） |
| **误杀率** | 误杀 / 拦截命中 | 周报，决定调阈值 |
| **漏放率** | 漏放 / 真违规 | 月度，决定扩 corpus |
| **策略覆盖率** | 已配策略 / 应配策略 | 季度，杜绝业务残留 |

> 注意：**漏放比误杀危险得多**——误杀最多掉 CSAT，漏放可能 S1 出事故。所以**先求漏放为 0，再求误杀最低**。

### 4.2 误杀率的三层定义

| 层 | 定义 | 计算方式 |
|----|------|----------|
| **回答级** | 拦截命中里人工判定可放行的占比 | 每周抽 200 条人工标注 |
| **用户级** | 误杀用户 / 总用户 | 月度 + 用户分桶（VIP 用户**单独看**） |
| **价值级** | 误杀带来的 CSAT / GMV 损失 | 季度业务联评 |

> 小智 v1.4 没量「回答级误杀率」，CSAT 跌了一周才发现——教训：**误杀率必须每周抽检进周报**。

### 4.3 阈值调参的「三道线」

| 阈值类型 | 三道线 |
|----------|--------|
| **内容安全**（辱骂/违规） | 漏放为 0 是硬线，误杀可接受到 10% |
| **PII / 合规** | 漏放为 0 是硬线，误杀可接受到 20%（可脱敏） |
| **主题 / 风格** | 误杀优先（伤 CSAT），漏放可接受 1–2% |
| **越狱 / 注入** | 漏放优先（防 S1），误杀可接受到 30% |

> 同样 0.85 的阈值在不同类护栏下意义完全不同——**阈值必须按类分级**，不能用全局阈值。

### 4.4 落地示例：误杀率抽检工程（Node.js + TS）

```typescript
// false-positive-sampler.ts —— 周度抽检
export async function sampleFalsePositives() {
  // 1) 取上周全部"拦截命"且没被人工审核过的对话
  const blocked = await db.conversation.findMany({
    where: { blocked: true, auditStatus: "pending", createdAt: { gte: weekAgo() } },
    take: 500,
  });

  // 2) 抽 200 条送到标注平台（Label Studio）
  const samples = shuffle(blocked).slice(0, 200);
  await labelStudio.uploadTask({
    project: "moderation-fp",
    samples: samples.map((s) => ({
      id: s.id, input: s.query, output: s.response,
      decision: s.decision, reason: s.reason,
      task: "判断这条拦截是否合理：是/否 + 理由",
    })),
  });

  // 3) 收标后算三类指标
  const labels = await labelStudio.fetchLabels("moderation-fp");
  const fpRate = labels.filter((l) => l.answer === "否").length / labels.length;
  recordMetric("moderation_fp_rate_weekly", fpRate);

  // 4) 超阈值告警
  if (fpRate > 0.30) alert("moderation_fp_high", { rate: fpRate });
}
```

### 4.5 「撤桶」流程：误杀发生时的快速回收

当某条策略引发 5% 误杀，必须能 **5 分钟内回滚**，而不是发版：

```typescript
// policy-registry.ts —— 策略版本化 + 灰度 + 回滚
type Policy = { id: string; version: number; status: "draft" | "canary" | "stable" | "rolled_back" };

export async function canaryAndRollback() {
  // 1) 新策略先 canary 5% 流量
  await policyStore.update("moderation.topical", { status: "canary", trafficPct: 0.05 });

  // 2) 看 30 分钟内的 FP 率 / 漏放率
  setTimeout(async () => {
    const fpRate = await getRecentFPRate("moderation.topical");
    if (fpRate > 0.30) {
      // 3) 自动回滚到上一个 stable 版本
      await policyStore.update("moderation.topical", { status: "rolled_back" });
      alert("moderation_rolled_back", { policy: "moderation.topical", reason: "fp_rate>30%" });
    }
  }, 30 * 60_000);
}
```

## 五、第三方与厂商 Moderation API 的取舍

### 5.1 三类可选方案

| 方案 | 代表 | 优点 | 缺点 |
|------|------|------|------|
| **通用 Moderation API** | OpenAI Moderation、Anthropic 内容过滤 | 快、开箱即用 | **中文差、与业务垂类不匹配、跨境延迟** |
| **开源分类器** | Detoxify-Large、Chinese-Text-Classifier | 可私有化、可微调 | 需自维护训练数据 |
| **专用小模型** | 业务标注 + BERT/DeBERTa 微调 | 准确率最高 | 训练成本高、需冷启动数据 |

> **生产推荐：自训练专用小模型为主，开源为辅，通用 API 仅做兜底**。原因见下。

### 5.2 准确率对比（同一语料 1000 条）

| 方案 | 中文 F1 | 英文 F1 | 时延 P95 | 成本 / 1k 次 |
|------|--------|---------|----------|-------------|
| OpenAI Moderation | 0.62 | 0.88 | 80ms | $0.04 |
| Detoxify-Large | 0.71 | 0.82 | 60ms | $0.01 (自托管) |
| **自训练 DeBERTa-zh** | **0.93** | 0.79 | 45ms | $0.005 (自托管) |

> 同样 1000 条，专用小模型 F1 高 31 个百分点，且成本只有 1/8。

### 5.3 坑点：vendor lock-in / 双跑期 / 中国境内

- **vendor lock-in**：把规则写死在 OpenAI 输出的 JSON 结构里——下次想换模型要改全链路；
- **双跑期必做**：新策略上线后必须与原策略并行跑 **2–4 周**，对比 FP / TP / F1——别盲切；
- **中国境内合规**：跨境调用第三方 Moderation API **存在数据出境风险**——金融/医疗/政务场景必须私有化。

> 架构原则：**护栏不耦合任何厂商**——判分器接在「输入/输出文本」上，换厂商只需要换判分器实现，业务 0 改动。

## 六、端到端落地示例：四周搭出小智护栏中心

### 6.1 四周排期

把本文所有零件排成四周（1 算法 + 1 工程 + 0.5 产品兼标注）：

| 周 | 动作 | 产出 | 指标变化 |
|----|------|------|----------|
| W1 | 梳理散落策略 23 条 → 4 类护栏策略表；建 1000 条语料（500 正 + 500 负） | 策略中心 v1 | FP/Rate 不变但 **可量化** |
| W2 | 部署自训练 DeBERTa-zh 主题 + 越狱两类判分器；同步/异步双层编排 | 判分器 v2 | FP 17.7% → 11.2% |
| W3 | 误杀率周报自动化（抽检 → 标注 → 算指标 → 告警）；策略版本化 + canary 5% | 运营平台 v3 | FP 11.2% → 6.4% |
| W4 | 撤桶流程 5 分钟自动化；策略覆盖率 100%；外部依赖全部解耦 | 护栏中心 v4 | FP 6.4% → 2.8%，CSAT 3.7 → 4.2 |

### 6.2 工具栈

| 环节 | 工具 | 备注 |
|------|------|------|
| 判分器训练 | Hugging Face Transformers + LoRA | DeBERTa-v3-zh 底座 |
| 判分器部署 | TorchServe / vLLM | 私有化 |
| 同步编排 | 自研中台 + Redis 流 | < 100ms |
| 异步审核 | Kafka + 独立 worker 集群 | 错峰 |
| 误杀率抽检 | Label Studio + 飞书/钉钉周报 | 每周一推送 |
| 策略版本化 | 策略中心表 + canary 路由 | 一键回滚 |
| 监控告警 | ClickHouse + Grafana + Alertmanager | FP/LP/拦截率分群 |

## 自检清单

- [ ] 护栏按 **主题 / PII / 内容 / 越狱 / 工具** 五类分别配置，没有混类；
- [ ] 策略 **不在 if-else**，在策略中心；改阈值不发布；
- [ ] 同步拦截 + 异步审核双层，高风险垂类走异步复审 + 撤回流程；
- [ ] 护栏分布在 **模型前 / 后 / 工具层三层**，互不耦合；
- [ ] 误杀率（回答级）每周抽检进周报，VIP 用户单独分桶；
- [ ] 漏放率月度抽检，漏放为 0 是硬线（先求漏放为 0，再求误杀最低）；
- [ ] 阈值按护栏类分级（内容 / PII / 主题 / 越狱各有不同容忍度）；
- [ ] 新策略必须 canary 5% + 30 分钟自动评估 + 异常自动回滚；
- [ ] 护栏实现与厂商解耦，**双跑期 2–4 周**，不盲切；
- [ ] 关键指标（拦截率、误杀率、漏放率、略覆盖率）进监控告警。
